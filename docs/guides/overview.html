Agent Identity Platform

A support copilot that has a real, cryptographic identity — instead of an API key — and whose every action is checked by policy, with a human approving the risky ones.

Guides: Overview For support reps For approvers

What it is, in plain language

You hire a contractor. You don't give them a master key that works on every door, forever, and that anyone can copy. But that is how most AI agents are given access today: a long-lived API key in a config file.

This platform does it the other way. The agent proves what it is using a short-lived identity that the platform itself issues and verifies. It acts on behalf of a person with a token that is narrow and expires in minutes. And every action is decided by a rulebook, not by the agent.

The one-sentence version

OAuth answers “is this actor allowed?” — identity answers “what is this actor?” — and an agent you can't identify is an agent you can't govern.

The cast

Who / whatWhat they do
The support rep (alice)Signs in and asks the agent to handle a ticket or a refund. Her authority is what the agent acts with.
The approver (manager)Reviews high-risk actions the agent wants to take, and approves or denies them.
The agentReads customer and order data, drafts replies, and can issue refunds. It holds no password or key.
The policy engineDecides, for every action, one of three things: allow, deny, or ask a human first.
The tool serversThe gate in front of the data. Nothing reaches the data without passing them.

What happens when the rep asks for something

  1. The rep signs in and gets a token that says who she is.
  2. The agent proves its own identity — the platform vouches for it, no secret involved.
  3. The agent trades the rep's token for a new, five-minute token that says “this agent is acting for this rep, for this service only”.
  4. The agent asks a tool to do the work.
  5. The tool asks the rulebook: may this agent do this for this person? The answer is no by default.
  6. If the action is risky, the run pauses until the approver decides — then it continues and the work is done.
  7. Every step is written down: who acted, for whom, what they asked for, and why it was allowed.

Why you can trust it

Built-in safety

There is no key to steal. The agent's identity lives for minutes and only works for that workload.

A stolen token is useless elsewhere. Each token is aimed at exactly one service; passing it along fails.

The model cannot overrule the rulebook. A clever prompt can change what the agent asks for, never what it is permitted to do.

Risky actions need a person. And that person cannot approve their own request.

Everything is written down — who did what, for whom, and why.

This is a demonstration

All the data here is synthetic — no real customers, cards, or personal data. The logins and passwords are demo values. In production these would be replaced by your own identity system and real integrations.
