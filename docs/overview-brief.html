Agent Identity Platform — a short brief

What an AI agent needs before you let it touch a real system: an identity of its own, limits it cannot argue with, a human in the loop for the things that matter, and a record of everything it did.

The problem

An agent that can issue refunds is dangerous in a way ordinary software is not. It decides which action to take rather than following instructions. It acts on behalf of a person, and should be able to do exactly what that person may do — no more. And it is instructed in plain language, which means its input is untrusted text that may contain instructions of its own.

The usual shortcut — give the agent a broad credential and trust the prompt — fails all three.

The principle: the model proposes, and something outside the model disposes. The model is never the security control. Replace it with a hostile one tomorrow and the platform refuses the same actions it refuses today.

What was built

A working platform on a local Kubernetes cluster, for an ordinary domain — a customer support desk that can look customers up and issue refunds. The interesting part is not the assistant; it is everything standing between the assistant and the money.

  • An agent that takes a plain-language task and can only use the tools the caller's role permits.
  • A tool server — the only thing that can touch customer data, and the only place where permission is really decided.
  • A rulebook (policy) answering allow / refuse / ask-a-human, read by both the agent and the tool server, versioned and signed so every decision records which revision decided it.
  • Approvals bound to one exact request, with no self-approval and no replay.
  • Identity for every workload, with no passwords or long-lived keys anywhere; the agent acts for the human with a short-lived, narrowly-scoped token rather than passing their credentials along.
  • A console where the security becomes visible: what your role allows, why a refund was held, who approved it, what has been looked at.
  • Guardrails and evals, plus traces, metrics and an audit trail that is cleaned of secrets and personal data before it is written.

How one request flows

A support agent types: "Refund $200 for order o-1001"
1. They sign in. Their token says who they are, their role, and their customer.
2. The agent verifies that token itself — right issuer, right audience, not expired.
3. A guardrail reads the task: empty, absurd, or an instruction-override attempt is refused before any model is called.
4. Policy is asked which tools this role may use. The model is offered only those, and told what it may not use, so it cannot silently pick something else.
5. The model proposes refunds.issue for $200. Its job ends here.
6. A second guardrail checks the proposal — a missing amount is refused, never guessed.
7. The agent trades the human's token for a short-lived one saying "the agent, for this human, in this customer". The original token is not forwarded.
8. The tool server verifies that token and asks policy the real question: may this role, in this customer, call this tool, with this amount?
9. $200 is above the automatic limit, so policy says: ask a manager. Nothing happens yet.
10. The run pauses and appears in a manager's queue, bound to that exact refund. A different person approves it.
11. The agent resumes carrying the approval. Everything is re-checked, the approval is valid for exactly this request, and the refund runs.
12. One audit record: who, for whom, which customer, which tool, the decision, the reason, and which revision of the rulebook decided it.

Why the checks sit where they do. Steps 3 and 6 are convenience — a fast, clear answer for obvious cases. Step 8 is the control. Delete the guardrails, let a hostile model propose anything, and step 8 still refuses. The rule of the codebase is that the model's output is never treated as permission.

Decisions worth knowing

The model is never the control

The agent is offered only the tools the role permits, and told what it may not use — so it cannot quietly substitute one action for another. Refusing beats improvising: a $1,000 refund silently downgraded to a lookup would look like success while doing something else.

Uncertainty resolves towards "no"

A missing amount, a value that is not a number, a blank field, an unreachable policy engine — all refuse. Each of these was a real bug, each of which had let something through by being treated as "probably fine".

An approval is bound to a request, not to a person

Recording "a manager approved a refund" would be simpler and could be reused. Binding it to the exact tool, arguments, human and customer makes replay impossible.

Audit is cleaned at the source

Redaction happens where a record is created, not where it is read. Anything else is a promise you must keep in every future reader, forever.

What verifying it found

Every item below was found by running the platform and disbelieving the result — not by reading the code. They are the most useful thing in the repository: a list of the ways this kind of system goes wrong.

  • The setup script did not restart the services it had just reconfigured, so changes silently did not take effect.
  • The sign-in server dropped a custom attribute, so roles and customers vanished from tokens and permissions were evaluated against nothing.
  • Workload identities were registered per service rather than per instance, so a new replica could not get an identity — visible only when you scale.
  • A certificate reloaded in-process just before expiry worked in tests and broke after about a day in a long-running process.
  • Policy allowed a refund through with a missing, null or dash-shaped amount.
  • Two audit fields were missing the customer, so an oversight view silently dropped the events it existed to show.
  • The audit trail was held in memory per replica: with two replicas, each held a different half of the events, and a restart erased them. An oversight view built on that is not incomplete, it is wrong.
  • An access check was misread as a stale deployment when the real cause was a missing field — nothing could prove which version was running, so build identity was made verifiable.

Almost every one of these was a case of the system appearing to work. That is why the repository now contains scripts that prove its claims: an attack suite, a customer-isolation suite, a role check, a transport check, a redundancy check, a secrets scan, and a build-identity check.

What is deliberately not built

Stated plainly, because a reference implementation that hides its edges teaches the wrong lesson.

  • Some infrastructure is single-instance. The identity server, sign-in server and database each run as one copy; losing one takes the platform down until it returns. Making them highly available needs shared storage and an external key service — real work, deliberately out of scope, and written down rather than implied.
  • The model is small. It sometimes declines a task it could have done. That is a quality limit, not a security one: enforcement does not care how good the model is.
  • The systems the agent acts on are simulated. There is no real billing system behind the refunds — the point is the identity, policy and approval machinery.
  • Some attribution depends on the model. When a request is refused before reaching the tool server, the record can only name the tool if the model asked for one by name. A small model often just declines. Guessing from the request text was considered and rejected: a keyword guess would give a privacy view exactly the false confidence it must not have.
  • Demo credentials are in the repository — fictional users with known passwords, so anyone can run it. The production pattern for secrets is a separate, real mechanism.

Running it

Docker, a local Kubernetes cluster tool and the model runtime, then one command to bring it up and a handful of scripts that check it behaves:

./start.sh — bring the platform up and print the console URL
scripts/demo.sh — the happy path: ask, get held for approval, approve, complete
scripts/attack-tests.sh — six attacks, all of which must be blocked
scripts/tenancy-tests.sh — one customer cannot reach another's data
scripts/role-tools.sh — each role gets exactly the tools it should
scripts/tls-check.sh — every internal connection is encrypted and authenticated
scripts/ha-check.sh — replicas are spread out, and losing one is survivable
scripts/check-images.sh — the running services are the build you think they are
