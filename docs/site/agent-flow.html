The agent, end to end

A task arrives as a sentence. What comes out is an answer, a refusal with a reason, a question waiting for a person, or a held action waiting for a different person to decide — after one tool call, or several, each of which policy judged on its own. This page follows that path through the code — the model proposes, the platform disposes — and shows exactly where each decision is made, and which control would catch it if the model were wrong.

Why this shape at all An autonomous agent is a program that decides what to do next, which means the interesting question is never "can it?" but "what happens when it decides something stupid, or is talked into it?" Every arrow below exists to answer that. Nothing here trusts the model with authority; the model is a proposer, and the platform around it is the authority.
There is one agent Everything on this page describes a single agent workload — one SPIFFE ID, one graph, one tool catalogue, held by two interchangeable replicas. Many runs happen at once, all as the same agent acting for different people. Policy trusts exactly that one ID, so a second agent is a policy change, not a config flag; the overview page has the detail under Workload identity.

The cast, and who may talk to whom

Four controls, four jobs

Guardrails refuse obvious rubbish before the model is even called. Policy decides whether this caller may call this tool with these arguments. Approvals hold the risky cases for a person. The tool server is where all of it is actually enforced — the model's opinion never reaches it unchecked.

Why not just ask the model not to?

Because a prompt is not a control. A model can be talked into things, and a small local one frequently is. Every control below is code that would work the same if the model were actively hostile — that is the test each of them passes.

2 · The graph

The agent is a small state machine, not a conversation. Four nodes, and the only interesting structure in it is the loop back from a person's decision into the tool call. Everything the model contributes happens in the first node; everything after it is the platform doing its job. 

    plan ──▶ call_tool ──▶ (ok / denied / error) ──▶ END
                 │  ▲
                 │  └── ok + "more" ──▶ plan (with what it learned, max 3 steps)
                 │
                 ├─ approval_required ──▶ create_approval ──▶ await_decision
                 │                                                  │
                 │                     approved ──▶ call_tool ◀──────┤
                 │                     denied   ──▶ END        ◀──────┘
                 │
                 └─ missing an argument ──▶ ask_clarification ──▶ call_tool
                                                  ▲              │
                                                  └── still missing ┘

the topology comment at the top of app/agent/graph.py

Four decisions worth noticing in that little diagram · create_approval is a separate node from await_decision: the interrupt node re-executes when the run resumes, so it must have no side effects. Creating the approval is a side effect; pausing is not.
· If the model produces nothing usable, the graph ends refused or error — it does not substitute another action. A refund request must never quietly become a customer lookup.
· A missing argument is the one gap the graph asks about rather than ending on, because the value is held by a person who is right there. The answer is merged in and the call still goes to policy — asking is not authorizing.
· More than one step is opt-in from the model, bounded at three, and every step is a full visit through the same enforcement point. A run that does not ask stops after one call, exactly as it always did.

The state it carries

Thirteen fields, and no place to hide a surprise — a run either names a tool and arguments, or it names why it did not.

app/agent/graph.py

class AgentState(TypedDict, total=False):
    task: str
    tool: str
    args: dict
    reason: str
    status: str  # ok | denied | refused | error | approval_required | approved | clarification_required
    refused_tool: str  # what the model asked for, when we know
    result: dict
    approval_id: str
    missing: list[str]  # required arguments still to be supplied by a person
    asks: int  # how many times we have asked for them
    steps: int  # how many tool calls this run has made
    observations: list[dict]  # what each of those calls returned, in order
    more: bool  # the model asked for another step after seeing the result
    final: bool  # the graph decided this step ends the run

plan — the only node the model influences

It asks the deps for a decision and copies it into state. Note what it does not do: it never picks a fallback tool, it keeps "the agent declined" apart from "something was broken" — those two end up on different dashboards at 3am — and when the only thing missing is an argument, it routes to a question rather than an ending. On a second pass it hands the model what the earlier calls returned.

app/agent/graph.py

def plan(state: AgentState) -> dict:
    # A second pass carries what the first call returned, so the model decides
    # with its eyes open rather than from the task text alone.
    decision = deps.decide(state["task"], state.get("observations") or [])
    if decision.get("clarify"):
        # The model named a tool it may use and lacked an argument a person
        # can supply. Ask, rather than refuse — but note what this does *not*
        # do: it never fills the value, and it never authorizes anything. The
        # answer is merged into args and the call still goes to policy.
        return {
            "tool": decision["tool"],
            "args": decision.get("args", {}),
            "missing": list(decision.get("missing") or []),
            "asks": state.get("asks", 0),
            "status": "clarification_required",
            "reason": decision.get("reason", ""),
        }
    if not decision.get("tool"):
        # The model produced no usable decision. Do NOT quietly do something
        # else — a refund request must never turn into a customer lookup.
        #
        # "refused" and "error" are different things to whoever is on call:
        # a refusal is the agent declining to act (the role may not call what
        # was asked for), an error is something being broken (the tool server
        # or the model was unreachable).
        return {
            "status": "refused" if decision.get("refused") else "error",
            "reason": decision.get("reason", "no tool was selected"),
            "refused_tool": decision.get("refused_tool", ""),
        }
    return {
        "tool": decision["tool"],
        "args": decision.get("args", {}),
        "reason": decision.get("reason", ""),
        "more": bool(decision.get("more")),
        "final": False,
    }

call_tool — where the platform takes over

The graph's only job here is to not crash, to record what happened so a second step can use it, and to refuse to repeat itself. That last part is a control, not tidiness: a repeated call is a repeated action — a second refund — so the check sits in the node that acts, where no route can bypass it.

app/agent/graph.py

def call_tool(state: AgentState) -> dict:
    # A downstream failure (e.g. the token exchange is refused) must become a
    # reported error, not an unhandled exception that 500s the request.
    previous = (state.get("observations") or [{}])[-1]
    if (
        state.get("observations")
        and previous.get("tool") == state.get("tool")
        and previous.get("args") == state.get("args")
    ):
        # The model asked for a call it has already made. Repeating it would
        # be a second real action — a second refund — for no new information,
        # so this stops instead. It is the only place that can enforce that:
        # by the time the router runs, the call would already have happened.
        return {
            "status": "ok",
            "result": previous.get("result", {}),
            "reason": "the same call was already made — stopping rather than repeating it",
            "final": True,
        }
    try:
        outcome = deps.call_tool(state["tool"], state["args"], state.get("approval_id"))
    except Exception as exc:  # noqa: BLE001
        # `final`, like everywhere in this node: a failure is not a step, so
        # there is nothing to observe and no reason to go round again.
        return {"status": "error", "reason": f"tool call failed: {exc}", "final": True}
    update: dict = {
        "status": outcome.status,
        "result": outcome.result or {},
        "reason": outcome.reason,
        "final": True,  # unless the model asked for another step below
    }
    if outcome.status == "ok":
        # Only a call that *happened* is a step, and only a step can be
        # observed — a denial or a hold teaches the model nothing about the
        # task, so a run cannot loop on those.
        update["steps"] = state.get("steps", 0) + 1
        update["observations"] = [
            *(state.get("observations") or []),
            {"tool": state["tool"], "args": state["args"], "result": outcome.result or {}},
        ]
        update["final"] = not state.get("more")
    return update

create_approval, await_decision, ask_clarification — the pauses

The split is the whole point. create_approval runs once and writes the request down; await_decision calls interrupt() and is re-entered on resume, so it must not do anything the second time around. ask_clarification follows the same rule for the other kind of pause — merging a person's answer, never inventing one.

app/agent/graph.py

def create_approval(state: AgentState) -> dict:
    try:
        approval = deps.create_approval(state["tool"], state["args"], state.get("reason", ""))
    except Exception as exc:  # noqa: BLE001
        return {"status": "error", "reason": f"could not request approval: {exc}"}
    return {"approval_id": approval["id"]}

def await_decision(state: AgentState) -> dict:
    decision = interrupt(
        {
            "type": "approval_required",
            "approval_id": state["approval_id"],
            "tool": state["tool"],
            "args": state["args"],
            "reason": state.get("reason", ""),
        }
    )
    approved = bool((decision or {}).get("approved"))
    return {"status": "approved" if approved else "denied"}

app/agent/graph.py

def ask_clarification(state: AgentState) -> dict:
    """Pause for the arguments only a person can supply.

    Pure, like `await_decision`: the interrupt re-executes on resume, so this
    must not write anything the second time around.
    """
    answer = interrupt(
        {
            "type": "clarification_required",
            "tool": state["tool"],
            "args": state["args"],
            "missing": list(state.get("missing") or []),
        }
    )
    supplied = (answer or {}).get("values") or {}
    # Empty strings count as no answer: a blank form is not a value.
    args = {**state["args"], **{k: v for k, v in supplied.items() if v not in (None, "")}}
    remaining = [name for name in state.get("missing", []) if args.get(name) in (None, "")]
    asks = state.get("asks", 0) + 1
    if not remaining:
        return {"args": args, "missing": [], "asks": asks}
    if asks < MAX_ASKS:
        # A partial answer is worth one more question — asking is cheaper and
        # kinder than refusing on a technicality.
        return {"args": args, "missing": remaining, "asks": asks}
    # Out of asks. This is a refusal, not an error: nothing is broken, the
    # agent simply will not invent an identifier.
    return {
        "args": args,
        "missing": remaining,
        "asks": asks,
        "status": "refused",
        "reason": (
            f"{state['tool']} still needs {', '.join(remaining)} "
            "after asking — nothing was executed"
        ),
    }

The routers, and the wiring

Six tiny functions that turn the state into the next node. after_call is where the loop lives, and it reads as three questions: was it held? did the model ask for more? can it still afford it?

app/agent/graph.py

def after_call(state: AgentState) -> str:
    if state.get("status") == "approval_required":
        return "create_approval"
    # Another step only when the model asked for one *and* the last call
    # actually happened (`final` is what call_tool sets), with the budget as
    # the backstop: three real actions is the ceiling for one request,
    # whatever the model says.
    if not state.get("final") and state.get("steps", 0) < MAX_STEPS:
        return "plan"
    return END

def after_create(state: AgentState) -> str:
    return END if state.get("status") == "error" else "await_decision"

def after_decision(state: AgentState) -> str:
    return "call_tool" if state.get("status") == "approved" else END

def after_plan(state: AgentState) -> str:
    status = state.get("status")
    if status in ("error", "refused"):
        return END
    if status == "clarification_required":
        return "ask_clarification"
    return "call_tool"

def after_clarification(state: AgentState) -> str:
    # The node leaves `missing` non-empty only while there is an ask left, so
    # the order of these two checks is what keeps the budget honest.
    if state.get("status") == "refused":
        return END
    return "ask_clarification" if state.get("missing") else "call_tool"

Why the graph is testable without a cluster Everything the nodes need sits behind AgentDeps — three methods: decide, call_tool, create_approval. The real implementation talks to the model, the tool server and the api; the test one returns a fixed plan and queued responses. That is why the safety properties below can be asserted deterministically in CI instead of hoped for in a demo.

3 · What the model sees, and what it may answer

The model is given a prompt built from the tools its caller's role actually has, plus a list of the ones it does not. It answers with JSON. That is the entire interface — it never sees the policy, the audit log, the approval queue, or another user's data.

The prompt

app/agent/llm.py

def _prompt(
    task: str, tools: dict, unavailable: dict | None = None, observations: list[dict] | None = None
) -> str:
    parts = [
        "You are a customer-support agent. Choose exactly one tool from the "
        "available list to handle the task.\n",
        f"Available tools:\n{_tool_manifest(tools)}\n\n",
    ]
    if unavailable:
        # Naming the forbidden tools matters: if we simply hide them, a small
        # model substitutes a different (allowed) tool and the run *looks* like it
        # succeeded — which is exactly the confusion this avoids.
        parts.append(
            "NOT permitted for this user's role (never choose these):\n"
            f"{_tool_manifest(unavailable)}\n\n"
        )
    if observations:
        # A second pass: the model is shown what its own calls returned, which is
        # the whole point of allowing more than one step.
        parts.append(
            "You have already done this for the task, in order:\n"
            f"{_observations_text(observations)}\n\n"
        )
    parts.append(f'Task: "{task}"\n\n')
    parts.append(
        "If the task needs a tool that is not permitted, or none of the available "
        'tools fits, reply with {"tool": null, "reason": "<why>"}.\n'
        "If a required argument is not in the task, still name the tool and leave "
        "that argument out — never invent one; the user will be asked for it.\n"
        "Otherwise reply with ONLY JSON of the form "
        '{"tool": "<name>", "args": {<arguments>}, "reason": "<short reason>", '
        '"more": true if you will need another call after this one}.'
    )
    return "".join(parts)

Each line of the manifest is generated from the catalogue, so the prompt cannot drift from what exists:

The more flag is only in the template, and that was learned the hard way The first version of this prompt described the flag in a sentence — "if you will need another call after seeing this one's result, add "more": true" — and the model ignored it on every run, while saying in its own reason that it needed the ticket before it could refund. Moving the field into the reply template made it emit "more": true for two-step tasks and false for one-step ones. Show a small model the shape of the answer; do not describe it.

app/agent/llm.py

def _tool_manifest(tools: dict) -> str:
    lines = []
    for tool in tools.values():
        required = tool.input_schema.get("required") or []
        params = ", ".join(required)
        lines.append(f"- {tool.name}({params}): {tool.description}")
    return "\n".join(lines)


# A tool result can be large, and the prompt is rebuilt on every step, so each
# one is shown truncated. What the model needs is enough to decide the next move,
# not a full record — the run keeps the whole thing in its own state.
_MAX_OBSERVATION_CHARS = 600


def _observations_text(observations: list[dict]) -> str:
    lines = []
    for i, obs in enumerate(observations, start=1):
        result = json.dumps(obs.get("result", {}), sort_keys=True)
        if len(result) > _MAX_OBSERVATION_CHARS:
            result = result[:_MAX_OBSERVATION_CHARS] + "…"
        args = json.dumps(obs.get("args", {}), sort_keys=True)
        lines.append(f"{i}. {obs.get('tool')}({args}) -> {result}")
    return "\n".join(lines)

The three guardrails on the model's answer

These are deliberately small and deterministic. The point is not to out-think a model; it is to refuse the obvious cases cheaply, audibly, and without relying on a small model to behave.

app/agent/guardrails.py

# A task longer than this is not a task, it is an attempt to stuff the context.
MAX_TASK_CHARS = 2000

# Phrases that only make sense as an attempt to override the instructions. This is
# defence in depth: policy still decides what may run.
_INJECTION_PHRASES = (
    "ignore previous instructions",
    "ignore all previous",
    "ignore the above",
    "disregard previous",
    "disregard the above",
    "you are now",
    "reveal your instructions",
    "print your instructions",
    "show me your system prompt",
)

app/agent/guardrails.py

def check_task(task: str) -> None:
    """Refuse a task that should never reach the model. Raises GuardrailError."""
    text = (task or "").strip()
    if not text:
        raise GuardrailError("the task is empty")
    if len(text) > MAX_TASK_CHARS:
        raise GuardrailError(
            f"the task is too long ({len(text)} characters, limit {MAX_TASK_CHARS})"
        )
    lowered = text.lower()
    for phrase in _INJECTION_PHRASES:
        if phrase in lowered:
            raise GuardrailError(
                "the task looks like an attempt to override the agent's "
                f"instructions ({phrase!r}) — refusing it"
            )

app/agent/guardrails.py

def check_decision(tool: Tool, args: dict) -> list[str]:
    """Return the required arguments the model did not supply (empty means fine).

    A missing argument is not a fault, and it is not a guess to be made: it is a
    value only the person asking for the work may have. Since S18 the caller asks
    for it instead of ending the run — so this returns the names rather than
    raising, and the graph decides. What must never happen is inventing the
    value, which is what makes "same argument, supplied by a human" safe to treat
    exactly like one the model produced.
    """
    required = (tool.input_schema or {}).get("required") or []
    return [name for name in required if args.get(name) in (None, "")]
This is the line S18 moved — and it is the only one When a required argument is missing, the run no longer ends. It asks. Every other guardrail still ends the run, because a bad task or a forbidden tool has no answer to wait for; a missing argument is a value held by a person who is right there. What has not changed is the rule underneath: the value is never invented, the answer is still checked by policy, and an answer is not an approval.

Identifiers are passed along, never invented S20

"The value is never invented" turned out to need saying to the model, not just to the code that fills gaps. Reported from a real run: asked to refund $200 with no order named, the model answered {"order_id": "order_id", "amount": 200} — the field's own name as its value. The presence check saw a non-empty string, so nothing was missing, and a refund against an order literally called order_id went to a manager for approval.

The rule now: an identifier is kept only if the model has seen it — in the task, or in what an earlier call returned. Anything else is a guess, and a guess is not a proposal. "Seen" means the same identifier-shaped token (o-1001, c-100, t-5001), compared as a set rather than searched for in the text — because a retry of the same task against the model found the next hole: the task says "for order ", so a model answering "order_id": "order" had used a word the task contains. It was a word, not an identifier, and it no longer passes.

app/agent/guardrails.py

def identifier_args(tool: Tool) -> list[str]:
    """The tool's required arguments that name something that exists in the world.

    The convention is the `_id` suffix — `customer_id`, `order_id`, `ticket_id`.
    These are facts the model cannot reason its way to; it either saw one or it is
    guessing, which is the distinction `resolve_identifiers` enforces.
    """
    required = (tool.input_schema or {}).get("required") or []
    return [name for name in required if name.endswith("_id")]


def resolve_identifiers(
    tool: Tool, args: dict, seen: set[str], from_task: dict
) -> tuple[dict, list[str]]:
    """Keep only the identifiers the model could have seen — never let it invent one.

    `seen` is the set of identifiers the model has been shown: those written in the
    task, and those an earlier call returned in this run. A value outside that set
    is a guess rather than a proposal, so it is replaced by whatever the *task* said
    (if it said anything — the person's words outrank the model's) and otherwise
    removed, which routes the call into a question instead of an action against the
    wrong record.

    Membership of a set, not a search of the text: a model that answers
    `"order_id": "order"` has used a word that happens to appear in the task, and
    `"order_id": "order_id"` a field name that does not appear at all. Neither is an
    identifier, so neither is seen.

    Returns the corrected arguments and the names whose value could not have been
    seen, so the caller can record that it happened.
    """
    kept = dict(args)
    invented: list[str] = []
    for name in identifier_args(tool):
        value = kept.get(name)
        if value in (None, "") or str(value) in seen:
            continue
        invented.append(name)
        if from_task.get(name) not in (None, ""):
            kept[name] = from_task[name]
        else:
            kept.pop(name, None)
    return kept, invented

Three outcomes, and the third is the one that took a bug to find · the id came from the task → kept. · the id came from an earlier tool result → kept, which is what makes a multi-step run work. · the id came from nowhere → dropped, and if the task named one, the task's value replaces it — so the person's words outrank the model's guess. The audit records llm.identifier_invented with the argument name (not the guessed value): the behaviour is the signal, the guess is noise.

Filling gaps, without inventing a decision

Small models are unreliable at copying arguments out of the task text. The code pulls identifiers and amounts out with a regex — but only to fill arguments the model left empty, and only ones the tool actually declares, so the run reflects policy rather than the model's formatting.

app/agent/llm.py

# What an identifier looks like in this platform: a short prefix, a dash, digits
# (o-1001, c-100, t-5001). The same shape `_extract_args` reads out of a task, so
# "the task named one" and "this looks like one" cannot drift apart.
_ID_TOKEN = re.compile(r"\b([oct]-\d+)\b")


def _extract_args(task: str) -> dict:
    """Best-effort arguments pulled from the task text.

    Small models are unreliable at filling tool arguments, and a missing
    argument would make policy fall through to deny. These are used only to
    fill gaps the model left, so the run reflects policy rather than the
    model's formatting.
    """
    args: dict = {}
    ref = _ID_TOKEN.search(task)
    if ref:
        value = ref.group(1)
        args[{"o": "order_id", "c": "customer_id", "t": "ticket_id"}[value[0]]] = value
    amount = re.search(r"(?<![\w-])(\d+(?:\.\d+)?)(?![\w-])", task)
    if amount:
        args["amount"] = float(amount.group(1))
    return args


def _fill_gaps(tool, args: dict, task: str) -> dict:
    properties = tool.input_schema.get("properties") or {}
    extracted = _extract_args(task)
    for key, value in extracted.items():
        if key in properties and args.get(key) in (None, "", 0):
            args[key] = value
    # Coerce to declared types (models often emit numbers as strings).
    from app.common.schema import coerce_args

    return coerce_args(properties, args)

4 · Where the tools fit

Tools are where an agent's opinion turns into something that happened. On this platform they are all reached through one method, and that method is the only place authority is granted — so there is exactly one thing to audit for correctness.

The enforcement point, step by step

This method is reachable over HTTP (POST /tools/<name>) and over MCP, and both funnel here. The comments in it read as the checklist they are.

  1. Which workload is calling? Proved at the application layer, not just by the transport. A pod holding some identity cannot reach the tool server — the header must name it.
  2. Is there a user token at all? No token, no call.
  3. Is the token real, and is it for this tenant? Verified delegation, including expiry and policy version.
  4. Does the tool exist? An unknown name is denied before policy is even consulted.
  5. What does policy say? One question, with the identity and the cleaned arguments.
  6. Allow → execute. Deny → return the reason. Require approval → do not execute until the approvals service confirms a matching approval.
  7. Record it. Every outcome writes an audit event keyed on the SPIFFE ID, the user and the tenant.

def call(
    self, token: str | None, tool_name: str, args: dict, *, workload_token: str | None = None
) -> ToolResult:

    # transport already required a chain-verified SVID; this says *who*, so a
    # pod that merely holds some identity cannot reach the tool server. The
    # check is here rather than in a transport handler because both the HTTP
    # and the MCP interfaces call this one method.
    if workload.enabled():
        try:
            caller = workload.check(workload_token)
        except workload.WorkloadRejected as exc:
            audit("tool.workload_rejected", tool=tool_name, reason=str(exc)[:200])
            return ToolResult(Outcome.DENIED, tool_name, f"workload identity rejected: {exc}")

    if not token:
        return ToolResult(Outcome.DENIED, tool_name, "no token presented")

    try:
        delegation = self._verifier.verify(token)
    except TokenRejected as exc:
        audit("tool.identity_rejected", tool=tool_name, reason=str(exc))
        return ToolResult(Outcome.DENIED, tool_name, f"identity rejected: {exc}")

    tool = self._tools.get(tool_name)
    if tool is None:
        audit("tool.unknown", tool=tool_name, sub=delegation.user)
        return ToolResult(Outcome.DENIED, tool_name, "unknown tool")

    call_args = _clean_args(tool, args)

Three outcomes, and the agent treats them differently allow the action happens. deny the run ends with the policy's own reason — the same reason the audit recorded. require approval the run pauses; nothing has happened yet. A fourth path exists — the tool itself failing — and it is reported as an error, not a refusal, because "the vendor is down" and "you may not" are not the same message to a person.
And a fifth thing: the tool can answer that it could not do the work Allow is policy's answer, not the tool's. Reported from a real run: a $20 refund against an order that does not exist was allowed — allow is exactly what policy said — and the tool answered unknown order. The screen said "allowed" and the result was an error, which reads as success. Two changes, and neither reverses the underlying decision (a record that is not there is an answer, not a failure — there is a test that says so): the call is now reported as allowed — but nothing happened, and the tool's own answer is recorded (tool.reported_error). Before, the trail held only tool.allowed, so "did the refund actually happen?" had no answer in the audit.

5 · The human interrupt

When policy says require approval, nothing has happened yet. The graph writes the request down, pauses, and returns to the user with the approval id. The run resumes only when a person with the manager role records a decision — and the tool server will not accept that decision on trust.

Pausing, and coming back

app/agent/graph.py

def run_task(agent, task: str, thread_id: str, user_token: str) -> dict:
    """Start a run. Returns the final state, or an approval-required payload."""
    config = {"configurable": {"thread_id": thread_id}}
    result = agent.invoke({"task": task}, config=config)
    return _shape(result)

def resume_task(agent, thread_id: str, decision: dict) -> dict:
    """Resume a paused run with a human's answer.

    One method for both pauses: an approval sends `{"approved": bool}`, a
    clarification sends `{"values": {...}}`. The run's state is durable; the
    token to act with is not, which is why the caller passes it again.
    """
    config = {"configurable": {"thread_id": thread_id}}
    result = agent.invoke(Command(resume=decision), config=config)
    return _shape(result)

def _shape(state: dict) -> dict:
    interrupts = state.get("__interrupt__") or ()
    if interrupts:
        payload = interrupts[0].value if hasattr(interrupts[0], "value") else interrupts[0]
        if isinstance(payload, dict):
            # The payload's own type decides the status: an approval and a
            # clarification both pause the run, but they are different things to
            # the caller — one settles a permission, the other supplies a fact.
            return {"status": payload.get("type", "approval_required"), **payload}
        return {"status": "approval_required"}
    return {
        "status": state.get("status", "unknown"),
        "tool": state.get("tool"),
        "result": state.get("result", {}),
        "reason": state.get("reason", ""),
        "refused_tool": state.get("refused_tool", ""),
    }
One pause mechanism, two payload types The checkpoint, the durable state and the Command(resume=…) are the same for both. What differs is the payload's type — approval_required or clarification_required — which is what the caller branches on, and why the caller can tell a question from a permission.

The api is a thin, proved hop in front of that: the browser talks to /tasks, the api forwards to the agent over a SPIFFE hop of its own, and the user's token rides along because it is what the agent acts for.

What an approval is bound to

The tool server does not trust a flag in the request body saying "approved". It asks the approvals service to confirm that an approval exists and matches this exact request — all six fields together:

What that prevents

An approval for a $60 refund cannot be replayed for $600 — the args are part of the match. An approval granted for one customer cannot be used for another — the user and tenant are too. And an approval cannot be borrowed by a different agent.

Why it is a service call, not a signature

The approvals service is a peer inside the trust domain with its own SPIFFE identity and a verified workload — so confirming an approval is an authenticated HTTP hop with no key material to manage, and no signature scheme to get wrong.

Who may decide, and who may not

Separation of duties is enforced, not requested The route requires the manager role, and the store refuses a decision from the same person who made the request — the 409 says so explicitly. This is the property that makes require approval mean something: the person who wants the action cannot be the person who authorizes it, and the platform checks that rather than trusting the UI to hide the button.

6 · The policy decision

There is one policy, written in Rego, and two callers asking it different questions. That is what keeps the tools the agent offers and the tools a caller may actually use from drifting apart.

9 · What the upgrade would change

Both halves are now built — this section is the record of how they changed Clarification (Tier 2) shipped as S18 and the bounded loop (Tier 3) as S19, so the rest of this page describes them as current code; what follows is what each change was, what it cost, and what deliberately did not move. Neither altered what is permitted: they change what the agent does when the task is thin or the answer arrives in more than one step.

The two gaps today

1 · It refused instead of asking built · S18

"Refund that customer" — with no order named — ended as a refusal, because check_decision required the arguments and it was right to refuse rather than guess. But the information exists: the person has it, and they are right there.

2 · It took one step built · S19

"Refund the customer from the last ticket" needs twice through the loop: read the ticket, learn the order, then ask for the refund. Before, the model had to guess both from the sentence in a single pass, and a small one usually would not.

Tier 2 — clarification, using the mechanism that already exists built · S18

The interrupt was never an approval feature; it is a general "pause and resume with a human's answer" feature. A clarification turned out to be the same operation with a different payload — which is why it needed no new checkpointing, no new durability story, and no new client protocol. It is now the code in sections 2, 3 and 5.

What actually had to change, against what was predicted here: the missing-argument branch of check_decision stopped being terminal; plan gained a clarification branch and a new node and router; _shape began reading the status from the payload's own type; resume_task took a decision instead of a boolean; the service grew a second resume shape and an agent.clarification_requested audit event; the UI grew a question card; and the eval case was rewritten deliberately. The bound — two asks — and the rule that a forbidden tool is still refused outright were added on the way. See the annotated run.

Tier 3 — one observation loop, bounded built · S19

Built as predicted: one new edge, call_tool → plan, with what the call returned carried in state. Two things were decided while building it, and both are worth knowing because they are the difference between this and the naive version:

The loop is opt-in, not automatic

The planned design had every successful run go round again so the model could say it was finished — which would have made a single-step task take two model calls and end as answered rather than ok, changing the outcome contract the demo, the UI and the tests all read. Instead the model says up front that it will need another look ("more": true), and a run that does not ask stops after one call, exactly as before.

The same call is never made twice

A repeat is not a wasted round trip, it is a second action — a second refund. The check lives in the node that acts, before the call, so no routing can bypass it, and it only looks at calls that actually happened: the held attempt of an approved refund is not a repeat of anything.

The router, as it is now — the loop is the middle question:

app/agent/graph.py

def after_call(state: AgentState) -> str:
    if state.get("status") == "approval_required":
        return "create_approval"
    # Another step only when the model asked for one *and* the last call
    # actually happened (`final` is what call_tool sets), with the budget as
    # the backstop: three real actions is the ceiling for one request,
    # whatever the model says.
    if not state.get("final") and state.get("steps", 0) < MAX_STEPS:
        return "plan"
    return END

And the budget itself, with the reason it is three:

app/agent/graph.py

# How many tool calls one run may make. Three: enough for "read the ticket, look
# up the order, issue the refund", and few enough that a model looping on itself
# cannot do much damage or cost much before the graph stops it.
MAX_STEPS = 3

What does not change

UnchangedWhy it can stay unchanged
Policy and thresholdsThe loop decides what to attempt; policy still decides what happens, on every attempt
The enforcement pointEvery step of the loop is still one call through the same method, with the same checks
Approval bindings, separation of dutiesThe loop neither issues nor verifies approvals — it can only ask again
The audit trailMulti-step runs produce more events, not different ones; each is still keyed on the same identity
Fail-closed behaviourAn unreachable policy still offers nothing, in a loop no less than before
Checked, not assumed A single-step run still makes one model call and one tool call and ends ok — there is a test whose whole job is that nothing changed for it. The budget stops a run that would never stop on its own. A recorded repeat is refused, and an approval in the middle is a pause rather than the end of the task.
The last thing worth saying about the upgrade A loop makes the agent more capable, and it makes the audit trail more important, not less: a run that reads a ticket to find an order and then issues a refund is two recorded actions where there used to be one. That is a reason the platform was built this way round in the first place — the intelligence is the part that is expected to change, and everything that constrains it is designed to be boring.

Glossary

delegationThe verified facts about a request: which user, which roles, which tenant, which workload is acting. The only source of truth a tool call has about "who".
SPIFFE IDA workload's name, e.g. spiffe://acme.com/ns/agent-platform/sa/agent. Both ends of every internal hop present one.
SVIDThe credential behind that name — X.509 for mTLS, JWT when a token must be passed along.
interruptThe graph's pause. State is checkpointed, the run returns to the caller, and Command(resume=…) continues it — the node re-executes, so it must be side-effect free.
enforcement pointThe one method where authority is granted. Everything above it proposes; nothing below it re-decides.
require_approvalPolicy's third answer. Not a denial — a hold, until a person with the manager role approves that exact request.
clarificationA pause for an argument only a person has, not for a permission. It is bounded (two asks) and the answer is judged by policy like any other argument — answering is not approving.
observationWhat one tool call returned, kept in the run's state and shown to the model on the next step. Only calls that happened produce one, which is why a run cannot loop on a denial.
identifierAn argument that names something real — customer_id, order_id, ticket_id. The model may pass one along if it has seen it, and never invent one (S20).
stepOne tool call that happened. Bounded at three (MAX_STEPS); a run that does not ask for more makes exactly one, as it always did.
refused vs errorRefused: the agent declined (the role may not do that). Error: something is broken (the model or a service was unreachable). Different messages because they are different problems.
fail closedWhen a control cannot reach its authority, it denies. No tools offered, no approval verified.
