Explained in plain language

Agent Identity Platform

An identity and authorization layer for AI agents. Agents here hold no API keys and no passwords. They prove who they are with a short-lived cryptographically issued identity, act on behalf of a specific person with a scoped token, and every action passes a policy check and, when it matters, a human decision — all of it recorded against the identity that did it.

SPIFFE workload identity OAuth 2.0 token exchange OPA policy as code Human approval Audit on identity Kubernetes
How to read this document It is written for a developer who has never seen the project: every acronym is defined where it first appears, and there is a glossary at the end. Sections 1–4 are the story; 5–13 are how each part works, with the real code; 14–18 are running, verifying and the project's own history, including its mistakes. Everything quoted here is from the repository itself — file paths are given so you can check.

The problem it removes

An agent that can act on a company's systems needs credentials to those systems. The usual answer is a long-lived secret — an API key in an environment variable, a password in a config file, a service-account JSON on disk. That answer has four problems, and they compound:

  1. A secret is a password, not an identity. It says "someone holds the key", not who is acting or on whose behalf. It cannot be scoped to one person, so anything the key can do, anyone who steals it can do.
  2. It never expires in practice. Rotating it means touching every place it is used, so it stays. A credential that might leak tomorrow is a credential that leaked yesterday.
  3. It is copied to wherever the work happens — a pod, a laptop, a CI runner, a log line in a stack trace. Each copy is another way to leak it.
  4. Nothing links actions back to a person. When the audit trail says "a refund was issued", the useful question — by whom, for whom, and was it allowed — has no answer.

This platform replaces the secret with identity: a workload receives a certificate that says what it is, usable only inside the cluster, expiring in an hour, never stored on disk. It acts with a token that names the user it is acting for and the audience it is meant for, valid for minutes. Policy decides what that combination may do, a human decides the risky cases, and the audit trail records the whole chain.

The claim, stated so it can be checked There is no static credential between the components of this platform. Not between the agent and the tools, not between the API and Keycloak, not between the services and the database. docs/threat-model.md lists eleven threats and names the test that addresses each; §17 shows how to run them.

The big picture

One pod per job, a shared identity system underneath, and two security regimes with a deliberate line between them: our own workloads prove who they are with SPIFFE, and third-party software we did not write is wrapped by a service mesh. The diagram is the whole architecture; the rest of this document explains each box.

The two regimes, and why

Our services are our code, so they can fetch a certificate, present it, and check the peer's name. Keycloak, OPA, Postgres and the sandbox are software we did not write: they have no idea what SPIFFE is, and bolting identity into them would be fiction. The mesh encrypts those hops instead. The reasoning is recorded as ADR-0012.

Where the line falls

The violet box is encrypted by us and checked by us — both sides present an SVID, and on the machine routes the caller also has to be named. The teal box is encrypted by the mesh, whose identity is the pod's, not the application's. The browser sits outside both: a person cannot hold a certificate, so TLS terminates at an ingress.

One request, end to end

Nothing explains a system like following a single action through it. This is the demo's central scenario: a support agent is asked to refund an order. Each step shows the real request and the real response, trimmed to the interesting fields.

  1. A person signs in. The browser posts credentials to the API, which exchanges them at Keycloak and returns a token the UI keeps in sessionStorage for the tab's lifetime. Note what comes back with it — the roles the platform will act on, and the tools those roles permit, resolved from policy:
    POST /auth/login → the session
    {
  "user": "alice",
  "roles": ["support_rep"],
  "tenant": "acme",
  "tools": ["crm.customer.read","crm.orders.list","refunds.issue",
            "refunds.quote","tickets.read","tickets.reply.draft"],
  "expires_at": 1789954090        // 300 seconds later (the realm's lifespan)
}
    The token is a bearer credential and lives five minutes. When it expires the UI says so and returns you to the sign-in screen rather than emptying its lists (§18 explains why that sentence is in a document like this).
  2. The task is sent. The browser calls POST /tasks with the token and a sentence: "Issue a refund of 200 dollars for order o-1001". The API does not do the work — it forwards the task to the agent, and that hop is a SPIFFE hop: the API presents its own certificate and a JWT that names it, so the agent knows which workload is calling (§11).
  3. The agent exchanges the token. It cannot use Alice's token directly: that token is for the API's audience. It asks Keycloak to exchange it (§6) for a token scoped to the tool server, carrying Alice's identity, her tenant and her roles, plus proof that the agent is acting on her behalf.
    the delegated token's claims (decoded)
    {
  "azp": "portal",
  "sub": "alice",
  "aud": ["mcp-tools", "spiffe://acme.com/ns/agent-platform/sa/agent"],
  "realm_access": { "roles": ["support_rep"] }
}
  4. Policy decides. The agent asks the policy engine what this role may do, and offers the model only those tools. When the model chooses refunds.issue with amount: 200, policy answers require approval — the demo's threshold is $50 outright, $500 with a manager, above that refused. The agent stops and records the reason in plain words:
    POST /tasks → held
    {
  "thread_id": "t-021609b2",
  "status": "approval_required",
  "tool": "refunds.issue",
  "args": { "order_id": "o-1001", "amount": 200.0 },
  "reason": "requires manager approval: refund of 200 is above the
             auto-approval limit of 50",
  "approval_id": "ap-100238f73f47"
}
  5. A human decides. The approval is a real row in Postgres, tenant-scoped, with the reason, the requester and the agent's SPIFFE ID. A manager sees it in the Approvals tab, may add a note, and approves or denies. The tool server will later check the decision itself — the UI is not the control (§8).
  6. The run resumes and the tool executes. The agent completes the run. The tool server accepts it only because a verified approval exists for exactly this tool, these arguments, this user and this agent:
    POST /tasks/resume → the result
    {
  "thread_id": "t-021609b2",
  "status": "ok",
  "tool": "refunds.issue",
  "result": { "id": "r-0014", "order_id": "o-1002", "tenant": "acme",
              "amount": 200.0, "status": "issued" }
}
  7. Everything is recorded. Each stage forwarded an audit event to the API, which stores them in Postgres after redaction. One record names the agent's SPIFFE ID, the user, the tool, the policy's decision, the policy revision that decided it, and when:
    GET /audit → one event
    {
  "ts": 1789953138.152,
  "event": "tool.allowed",
  "sub": "alice",
  "tool": "refunds.issue",
  "decision": "require_approval",
  "reason": "requires manager approval: refund of 200 is above the
             auto-approval limit of 50",
  "tenant": "acme",
  "spiffe_id": "spiffe://acme.com/ns/agent-platform/sa/agent",
  "policy_version": "a1e7b93"
}
    That last field is why policy is versioned: a decision recorded six months ago can be read next to the exact rule that produced it.
The shape to notice No component along that path holds a long-lived credential. The person has a password (theirs to protect). Every machine-to-machine hop is a certificate that expires within the hour or a token that expires within minutes. The one secret that does exist — the model provider's key — lives in a single service, the gateway, and never leaves it.

Workload identity

The foundation is a standard called SPIFFE (Secure Production Identity Framework for Everyone) and an implementation of it called SPIRE. The idea is simple: a piece of software running in your infrastructure should be able to prove what it is without being given a secret to prove it with.

The words, defined once

TermWhat it actually is
WorkloadAny program with an identity — here, a pod's main container. The agent, the API, the tool server are workloads.
Trust domainThe namespace identities are issued in. This platform's is acme.com, and it is documentation, not a secret.
SPIFFE IDA URI naming one workload: spiffe://acme.com/ns/agent-platform/sa/agent. Read it right to left: service account agent, in namespace agent-platform, in trust domain acme.com.
SVIDThe credential behind that ID. Two forms are used here: an X.509-SVID (a certificate, for TLS) and a JWT-SVID (a short signed token, for saying who is calling in a header).
Workload APIA Unix socket inside the pod. A workload asks it for its identity; it is not handed a password to use with it.
AttestationHow SPIRE decides a node and a pod are genuine before issuing anything — here, the Kubernetes projected service-account token, checked with the API server.
There is one agent, and the platform is built for exactly one One agent workload, one SPIFFE ID — spiffe://acme.com/ns/agent-platform/sa/agent — held by two replicas that are interchangeable: a run's state is checkpointed in Postgres, so either replica can resume it, and many runs run at once, all as the same agent acting for different people. Policy trusts exactly that ID (is_trusted if input.agent == trusted_agent in policy/authz.rego), so a second agent would be refused as an untrusted workload until it is registered and the policy names it. Everything else is already keyed per agent — the gateway's rate and cost limits, the audit's spiffe_id — which is what would make that a policy and manifest change rather than a redesign. It has not been written down until now; see the agent, end to end for the flow itself.

How a pod gets an identity

  1. The SPIRE agent runs on each node (a DaemonSet) and proves to the SPIRE server that it is a real agent on a real node, by presenting a Kubernetes service-account token the server checks with the API server. That is k8s_psat attestation.
  2. The server decides what that node's agent may vouch for, from registration entries: "a pod in namespace agent-platform using service account agent may be issued spiffe://acme.com/ns/agent-platform/sa/agent". scripts/setup.sh creates one entry per attested agent — because with more than one node, each node has its own agent, and an entry parented to a single agent leaves pods on every other node with "no identity issued".
  3. The pod's container asks the Workload API socket for its identity. It never presents a password to obtain it; the node's attestation is the root.
  4. What comes back expires — an hour for a certificate, five minutes for the JWT form — and the process fetches a new one when needed. Nothing is stored in a Kubernetes Secret, a config file, or an image.
app/common/server.py — every service starts by fetching its identity
def svid_files(socket: str) -> tuple[str, str]:
    """Fetch the X.509-SVID, retrying while SPIRE finishes attesting this pod."""
    last: Exception | None = None
    for _ in range(30):
        try:
            return write_mtls_files(socket)
        except Exception as exc:  # the Workload API may not be ready yet
            last = exc
            time.sleep(2)
    raise SystemExit(f"could not obtain an X.509-SVID: {last}")

Two details that came from incidents, not from the standard

Both of these are worth reading if you have ever trusted a certificate to keep working:

A server must restart before its certificate expires

The services do not merely fetch an SVID; they exit 120 seconds before the certificate they are serving expires, and the pod restarts with a fresh one. The deadline is read from the certificate's own notAfter, not assumed from its lifetime — the Workload API can hand back a certificate that is already half spent. A TLS server holding an expired certificate fails every handshake, which looks like an outage rather than a rotated credential (app/common/server.py, slice S15).

Keycloak needs a jti that SPIRE does not mint

The agent authenticates to Keycloak with a JWT-SVID as its client assertion (private_key_jwt, RFC 7523). That flow requires a unique jti claim per assertion so a replay is detectable — and SPIRE does not add one. The project builds a small CredentialComposer plugin (source in spire-plugin/, compiled into its own SPIRE server image) whose only job is to add it.

The agent image disables JWT-SVID caching on purpose SPIRE ships with an in-memory cache for JWT-SVIDs. This project builds its agent image without it, so a token is minted per use: revocation is a decision within five minutes, not a cache's lifetime. ADR-0002 records the trade — slightly more signing, a much smaller window of doubt.

Delegation, explained

Identity answers "who are you?". Delegation answers "who are you acting for, and what were you allowed to do?" The mechanism is OAuth 2.0 Token Exchange (RFC 8693): a token is traded for a different token.

Why trade at all? Because a token that works everywhere is a token worth stealing. The platform's rule is that every token names an audience — the service it is for — and only that service accepts it.

sdk/agentnhi/tokens.py — three checks, in order
1. **Signature and issuer** — it really came from our authorization server.
2. **Audience (`aud`)** — it was minted for *this* service. This is what makes a
   token stolen from one hop useless on the next.
3. **Issued-to (`azp`)** — it was issued to the workload we expect. Defense in
   depth: even with a matching audience, a token issued to someone else is
   refused.

The same delegation, traced (browser path)

browser ──token(aud=api)──▶ api
                              │  exchanges at Keycloak: "give me a token for mcp-tools,
                              │  for this user, issued to me (the agent)"
                              ▼
                           token(aud=mcp-tools, sub=alice, tenant=acme, roles=[support_rep],
                                 azp=portal, act={sub: spiffe://…/sa/agent})
                              │
                              ▼
                            tools   ← verifies signature, aud, azp, roles… then policy… then approval

The two questions every hop answers

A well-designed system asks both, and this one does, from different mechanisms:

QuestionAnswered byFailure looks like
Is the transport peer genuine? (a real workload, not something that copied a token)The SVID on both ends of the TLS connection (§11)The handshake never completes — there is no application-level "please authenticate" step to attack
Is it allowed to do this?Token claims (aud, azp, roles, tenant) plus policy, plus a verified approval where requiredA refusal naming the reason: your role may not call refunds.issue

And on machine hops, a name

A certificate proves a workload holds an SVID issued by the right authority; it does not say which workload. So the hops between the API, agent and tool server carry the caller's SPIFFE ID in a JWT-SVID, checked against SPIRE's public keys and an allow-list:

app/api/authz.py — the dependency that names a machine caller
def require_workload(*allowed: str):
    """Dependency factory: a **machine** caller must be one of these workloads.

    For the routes a workload calls rather than a browser (creating an approval,
    verifying one, ingesting audit). The name is the caller's JWT-SVID, verified
    against SPIRE's JWKS — the same check the gateway makes, shared via
    `app/common/workload.py`.
    """
Why that mattered Before this, POST /audit/events took no credential at all: any pod inside the mesh could write an audit record. The handshake was encrypted, which felt like enough, and said nothing about who was on the other end. Now only the agent and the tool server may ingest audit, and they have to prove it.

Everything expires, on purpose

CredentialLifetimeConsequence
Your sign-in token300 sThe UI revalidates the session and asks you to sign in again
JWT-SVID (a machine hop)5 minA machine call is refused if it presents none
Delegated token (a tool call)minutesThe agent refunds one tool call, not a week of them

These are the demo's numbers, chosen short so that rotation is visible during a demonstration. Production would use longer ones — the mechanism is the same.

Policy as code

Authorization is not scattered through the services as if user.is_admin. It is a policy written in Rego and evaluated by OPA (Open Policy Agent), so that the rules can be read, tested and versioned on their own (policy/authz.rego, ADR-0003).

Deny by default, three outcomes

Every tool call resolves to exactly one of: allow, deny, or require approval. Nothing needs a rule to be forbidden.

The matrix, and who may call what

The heart of the policy is a role → tool table. This is the demo's, verbatim from policy/authz.rego:

RoleTools it may call
support_repcrm.customer.read, crm.orders.list, tickets.read, tickets.reply.draft, refunds.quote, refunds.issue
billingcrm.orders.list, refunds.quote, refunds.issue
read_onlycrm.customer.read, crm.orders.list, tickets.read
privacyprivacy.pii.read, crm.customer.read, crm.orders.list, tickets.read
managercrm.customer.read, crm.orders.list, tickets.read, refunds.quote (and approving — not a tool)
platform_admin— deliberately none: it administers users, and administers nothing else

Two further rules make it more than a table. A tool can require approval rather than permission, and a tenant can replace a role's row with its own (slice S8) — so "billing" at one customer need not mean what it means at another. The API asks for the caller's tenant when it asks what is permitted, which is what keeps the offered set equal to the allowed set.

Rules that are numbers

policy/authz.rego — the refund rules, in full
auto_refund_limit := 50        # <= this: allowed outright
approval_refund_limit := 500   # <= this (and > auto): needs approval; above: denied

This is the mechanism the whole demo turns on. A $25 refund is allowed. A $200 refund is held for a manager. A $1000 refund is refused outright. The agent cannot talk its way past any of it: it does not evaluate the policy, it asks it — and the tool server asks again on the way through.

Where it is enforced — one choke point

Both transports (HTTP and MCP) pass through the same function, which is why a second transport cannot be a way around the first:

app/tools/enforcement.py — the enforcement point
1. **Verifies the token** — signature, issuer, audience, and the workload it was
   issued to.
2. **Asks OPA** — allow / deny / require-approval, deny by default.
3. **Requires a real approval** when policy demands one — confirmed by the
   approvals service, not asserted by the caller.
"The LLM proposes, policy disposes" The model is only ever offered the tools the caller's roles permit, so prompt-injection has nothing to aim at — and even if the model asked for something else, the tool server evaluates policy itself. The offer is a courtesy; the check is the control.

Versions and signatures

Every decision records policy_version — the revision the bundle was built from — so an old decision can be read next to the rule that produced it (docs/policy-lifecycle.md). The bundle is a build artifact: stamped by scripts/build-bundle.sh, signed with cosign, and mounted into OPA. Because the files are mounted with subPath (which does not update in place) the deployment restarts OPA when the revision changes — a small operational detail that is easy to get wrong, and is why the setup script does it explicitly.

The human in the loop

Policy can say "not without a person". That is the interesting case, because it is where a system most often cheats: it asks a UI for confirmation and treats the answer as authority. Here the approval is a fact recorded in the database, and the tool server checks the fact itself.

The shape of a held action

  1. The policy decision is require approval. The agent does not proceed and does not silently substitute another tool. It stops, with a reason written for a person to read: "requires manager approval: refund of 200 is above the auto-approval limit of 50".
  2. The run is checkpointed. The agent is a state machine (LangGraph, ADR-0004) whose state is persisted in Postgres — so the pause survives a restart of the agent itself, and resuming is not a matter of hoping the process is still alive.
  3. An approval record is created by the agent calling the API over a SPIFFE hop, with its own identity attached. The record names the tool, the exact arguments, the requesting user, and the agent's SPIFFE ID.
  4. A person decides — in the Approvals tab, or by API — optionally adding a note that becomes part of the record. The demo enforces separation of duties: you cannot approve your own request, and the platform_admin role cannot approve anything, because administering users is a different job from deciding business actions.
  5. The run resumes, and the tool server verifies. Not "the caller says it was approved" — the tool server asks the approvals service whether an approval exists for precisely this tool, these arguments, this user and this agent. A copy of a legitimate approval for something else is useless (threat T4).
Why "verify, don't trust" is the whole design The agent could lie; it is software, and software with a model in it can be talked into things. So no component downstream of the model is asked to believe anything the model influenced. The approval is checked against the database of approvals, and the identity of the checker is checked by the certificate it presented to get there.

What an approver sees

The UI shows each held action as a card: the tool, the arguments, the delegation chain (agent → user → tool), the reason policy gave, and a decision form with an optional note. Once decided, the card states the outcome prominently — approved in green, denied in red — for everyone looking at the run, including the approver who decided it.

One detail from the project's own history: that denial message used to be grey prose, rendered only for people who were not approvers — so the one person who could not see the denial was the manager who had just denied it, who fell through to a live Approve/Deny form and could decide the same run twice. §18.

The same gate for privacy

Reading a customer's personal data is a read, and a read cannot be undone. The privacy.pii.read tool therefore requires the privacy role and an approval, and every attempt — allowed or not — is written to the audit trail with the reason. docs/privacy.md walks the whole path, and the Privacy tab shows it as a timeline plus its own approvals.

The tool boundary

Every action an agent can take ends at one service. The tool server is where "the LLM proposes, policy disposes" is actually enforced (app/tools/) — and the only place it needs to be.

One implementation, two transports

TransportUsed byWhy
HTTPThe agent's direct tool callsSimple, inspectable, and easy to call from a test
MCP (Model Context Protocol)The agent, when it is given tools as an MCP serverAn open standard for exposing tools to models (ADR-0005) — adding it must not add a second way around policy

Both funnel through the same function, ToolEnforcer.call(...), which is the single place that verifies the token, names the calling workload, asks policy, and requires a verified approval. One choke point is why the MCP path cannot be a loophole.

The tools themselves are deliberately dull

Seven tools: read a customer, list orders, issue or quote a refund, read a ticket, draft a reply, and read personal data. They live in app/tools/catalog.py and call into app/simulators/ — synthetic CRM, orders, payments and ticketing data, which is all this platform ever touches (ADR-0006).

The sandbox stands in for a vendor

A real integration is a system you do not control, which may be slow, unavailable, or stateful in ways you have to remember. The sandbox is a small service with its own database and its own volume, and the tools reach it through a seam (simulator | http) that a real backend can replace without touching the rest of the platform (docs/integrations.md, slice S9).

Refusals, denials and errors are different things

A denial is policy saying no. A refusal is the agent reporting that it could not act — and it says why: an unreachable model, an unparseable reply and a disallowed tool are three different messages, not one. A tool error is neither: asking to refund an order that does not exist answers unknown order, because the platform was allowed to try and the vendor said no (slice S13) — which the UI reports as allowed, but nothing happened, since "allowed" is what policy said and not what the tool did. And a question is none of these: since S18, a task that is missing an argument the tool requires pauses and asks for it, rather than ending (see the agent, end to end).

Why this distinction earns its own slice "The agent didn't do it" is the least useful sentence an agent platform can produce. Every one of those cases has a different fix — a policy change, a network change, a prompt change — and telling them apart is the difference between a system you can operate and one you have to guess about.

The LLM gateway

The agent needs a model. The model provider needs a credential. If the agent held that credential, a prompt-injected agent — or a curious engineer with kubectl exec — could spend the company's model budget, and the key would have to be rotated wherever the agent runs. So the credential lives in exactly one service, and the agent is only allowed to ask that service for text (ADR-0009, docs/llm-gateway.md).

How the gateway decides who is asking

  1. The gateway listens only over mTLS with an SVID — there is no plain listener at all. A caller must complete a handshake with a certificate from the trust domain, so "who is calling" is never a matter of opinion.
  2. On top of that, the caller presents a JWT-SVID for the gateway's audience, verified against SPIRE's public keys. That is what makes the accounting exact: limits are keyed on the caller's SPIFFE ID, not on an API key shared by everything that can reach it.
  3. Rate and cost limits are applied per agent — a rate per minute and a token budget per day — and they are stored in Postgres, so a restart of the gateway does not reset them to zero.

Swapping the model

The model is named in exactly one place — a ConfigMap the gateway reads at startup, rendered from the gitignored .env — so changing it touches no manifest and rebuilds no image:

one command, local models
./scripts/use-model.sh qwen3:30b-a3b            # swap
./scripts/use-model.sh llama3.2:3b              # and back
./scripts/use-model.sh --eval qwen3:30b-a3b     # swap, then score it with the live evals

Which model you choose is not cosmetic. Measured with the eval suite on one machine: a 30B MoE scored 6/8, a 3B scored 4–5/8 — and the 3B's failures include "PII is refused for a support rep", a security guardrail rather than a nicety. The portable default in the repository is qwen3:30b-a3b; llama3.2:3b is a quarter of the size and much quicker.

Two things the first swap taught us A thinking model (Qwen3 and friends) puts its JSON in thinking and returns response empty, so the agent reported an unparseable reply while the model had answered correctly — the gateway now asks for think: false and falls back, which took that model from 1/8 to 6/8. And the audit had been recording the model the caller asked for, which is usually nothing: it now records the model resolved for the call, which is what makes "which model decided this?" answerable.

Provider-agnostic by construction

The gateway speaks an OpenAI-compatible API and a local Ollama endpoint. The default is local: ./start.sh needs no model key at all, which is why the platform runs end to end on a laptop with nothing in the cloud. If you set a provider key, it is consumed by the gateway and by nothing else.

The gateway is not on the internet It is deliberately absent from the ingress: only the agent should reach it, and only over mTLS. Push a conversation through the UI and the path is browser → ingress → api → agent → gateway; the provider credential never comes near a browser or the agent's own environment.

Transport security

Every hop is encrypted, but not by the same thing — and the line between the two mechanisms is deliberate, recorded in ADR-0012. Getting this wrong is easy in a way that looks right: a service mesh encrypts everything, so it is tempting to leave it at that. The catch is that the mesh proves the identity of the mesh. The application never learns which workload is on the other end, and a hop can be encrypted while a pod that copied a token walks straight through it.

LayerCoversThe identity it proves
SPIFFE mTLS (ours)Every hop between workloads we wrote: agent ⇄ gateway, agent ⇄ tools, agent ⇄ apiThe workloads' own SVIDs — and on machine routes, the caller's name
Service mesh (Linkerd)Everything else: Keycloak, OPA, Postgres, the sandbox, the observability stack, and the /metrics scrapeThe mesh's workload identity — good encryption, no name the application can use
TLS at the ingressThe browser's hop to the APIA certificate from a CA this project generates, with the hostname the browser types in it

Why the third-party hops stay on the mesh

Keycloak, OPA and Postgres are products we did not write: they do not speak SPIFFE and cannot present an SVID. Requiring one would be fiction. The sandbox stands in for a vendor's system, and a real vendor has no SVID either — so putting it with the third-party software models the right thing. For those, the mesh is the honest answer: no TLS code in the products, no certificates of ours to distribute, and it covers the hops you would forget, including telemetry.

One mechanical detail that matters

Our SPIFFE ports skip the mesh proxy The pods carry config.linkerd.io/skip-inbound-ports: "8443" (and the outbound equivalent). Without it, Linkerd terminates the connection — proving its identity and hiding the peer's SVID from our server, so the application's check has nothing to check. The fix is this project's own lesson, applied to itself, and tls-check.sh asserts the consequence: a client with no SVID cannot complete a handshake on a hop we own.
The alternative was measured and rejected The obvious way to keep the two identity systems from overlapping is to take our pods out of the mesh. Before doing that, the project measured it: with the API pod uninjected, a login still worked against a meshed Keycloak — in plaintext. A client without a proxy loses encryption on all of its outbound hops, not just the ones being retired. That measurement is why the pods stay injected and only the port is skipped.

How this is verified, rather than asserted

./scripts/tls-check.sh reports three things, each from where it can actually be seen:

./scripts/tls-check.sh

  agent → tools   mTLS required ✓    ✓ refused unnamed; admitted named (403)
  agent → api     mTLS required ✓    ✓ refused unnamed; admitted named (200)

The edge section deliberately uses the CA and never -k. A certificate nobody verified is not evidence, and "it answered over https" means nothing if we skipped the part that says who answered.

What this does not give you

ResidualWhy, and what to do about it
The ingress → api leg is plaintext in-clusterThe ingress controller carries no mesh sidecar, so the mesh cannot encrypt a connection it did not originate. Name it, and close it by meshing the controller (linkerd.io/inject: ingress) or terminating inside the mesh.
A machine caller's name rides a token, not the certificateOur ASGI server does not expose the peer certificate to the application, so the name travels as a JWT-SVID in a header: audience-bound, five minutes, never logged. The strongest form would be an X.509 SAN assertion, and that needs a different server.
The mesh remains load-bearing for third-party hopsLosing Linkerd removes their encryption, not their authorization — policy, tokens and tenancy are unaffected. This is a boundary, not a claim that there is only one identity system.

Multi-tenancy

Two customers use this platform. Neither may see the other's anything. The design decision that makes that enforceable is small and easy to miss: the tenant is part of the caller's identity, not a parameter they pass.

It comes from the token

A user's tenant is set when their account exists and travels in the token they present. There is no ?tenant= anywhere — which is what stops the oldest trick in the book, asking for someone else's data politely.

It is enforced everywhere it matters

Policy resolves a role's tools for that tenant (a tenant may replace a role's row entirely). Approvals are stored and queried per tenant. The audit trail is scoped to the caller's tenant. Every data accessor checks it.

The demo signs in grace — a support representative at a second tenant, globex — and ./scripts/tenancy-tests.sh walks the layers one at a time: the claim, the policy, the approval store, and the data itself:

acme is invisible in globex…  and the same customer id reads differently in each
tenant.                                            A second tenant's data is unreachable from the first.

Threat T9, and the reason the platform is "multi-tenant" rather than "multi-user with good intentions".

Data and durability

Nothing in this platform is stateful in memory, and that is a design position rather than an accident: a service can only be replicated — and therefore survive a node dying — if its state lives somewhere that outlives it (docs/ha.md).

Redaction happens before anything is written

Audit events are the one place where "we logged everything" becomes a liability: logs outlive the data they describe and travel to places with weaker access control. The platform redacts tokens and personal data before the record is stored, so the trail can name what happened and who did it without carrying the secret or the person's data with it (threat T7). The Audit tab states this on the page, because a reader deserves to know what they are looking at.

The honest limits of the demo's storage One Postgres instance, on a volume that is node-local (kind's local-path provisioner) — so it cannot follow its pod to another node, and deleting the cluster deletes it. That is fine for a demonstration and wrong for production, which is why the Helm chart takes a database.url pointing at a managed, replicated database. The distinction is documented rather than glossed: docs/data-stores.md.

Deployment

The whole platform runs on a laptop. ./start.sh creates a Kubernetes cluster (kind), builds the images, deploys everything, and prints a URL; the first run takes ten to fifteen minutes, and every run after it resumes in seconds. That is not a toy convenience — it is how the project stays honest, because a system you cannot bring up from scratch is a system whose instructions have quietly rotted.

Two faces of the same platform

kind — the whole thing, locally

One control plane and two workers, so replication and spreading are real rather than theoretical. No host ports are published on purpose, which is why the demo reaches the platform through a port-forward (and why that port-forward goes to the ingress, not the API).

The identity tier can be a failover pair

SPIRE's registration registry has lived in Postgres since the first hardening slice, but its CA key was a file on a volume — so two SPIRE replicas would each mint their own CA and hand out different trust bundles, which is worse than having one. The KeyManager is now switchable:

.env — the switch, and its default
SPIRE_KEY_MANAGER=disk      # default: no credentials, one replica, CA on a volume
# SPIRE_KEY_MANAGER=aws_kms # keys created, rotated and used inside AWS KMS
# SPIRE_KMS_ROLE_ARN=arn:aws:iam::…:role/spire-kms
# SPIRE_KMS_SERVER_ID=acme-com   # identical on every replica, or they mint separate CAs

With the key manager shared, the server scales to two replicas — and the setup gate refuses to pass unless they present the same trust bundle. The AWS side is a script (scripts/setup-aws-kms-role.sh) that creates a role holding the KMS permissions and a user whose only power is to assume it, with a self-test that makes the same call SPIRE makes first. The demo stays on disk: an unattended demo should not depend on credentials that expire.

Signing, and deploying behind a human

Releases sign the images and the policy bundle with keyless cosign (Sigstore): the signature is tied to the workflow that produced it and recorded in a transparency log, so there is no signing key to store, rotate, or leak (ADR-0010, docs/supply-chain.md). The deploy workflow then reverses the direction of trust: it verifies those signatures before applying anything, and the apply sits behind a GitHub Environment approval — a human gate on deployment, which is the same idea as the product's own approval gate, one level up.

Exceptions are meant to be temporary Trivy's ignore file currently has no entries, and the file says so along with the history: Keycloak once needed an exception for a read-only root filesystem because its development mode wrote into the image at startup. When the platform moved to production mode (slice S4), the cause went away — so the exception did too. A list of exceptions is a list of things you intend to fix.

Observability: the question the platform exists to answer

Traces and metrics are not decoration here. The interesting question is "which agent, acting for which user, asked for what, and what did policy decide?" — and that question spans services. Spans carry identity attributes, the API exports platform counters at /metrics, Prometheus scrapes them, and Grafana draws the dashboard:

agent_platform_logins_total result agent_platform_audit_events_total event agent_platform_approvals_pending agent_platform_http_requests_total method · route · status

The platform counters are derived from the audit stream, deliberately: every service forwards audit events to the API, so one ingest point yields policy decisions, approvals, logins and admin actions. The dashboard and the audit log cannot drift apart, because they are the same data.

The floor of two is not arbitrary: it matches the HA replica count, so autoscaling can never quietly take you below the redundancy you asked for, and scale-down is slowed so a short burst does not immediately drop capacity.

Self-healing, and the limit of a probe

Every container carries a liveness probe, not just a readiness one — because a readiness probe is a signal, and only liveness restarts a process. That distinction cost this project a day and a half of a broken bring-up (§18), and it is why the gateway serves a health-only plaintext listener: an mTLS-only service cannot be probed by a kubelet, which has no SVID to present.

The traps worth knowing before you operate it Rotating a Keycloak client secret in .env does not reach an existing realm (the realm is imported once and preserved, which is what keeps enrolled accounts) — delete the realm or the database and re-run. OPA reads its bundle at startup and the files are mounted with subPath, so a new revision needs a restart, which setup.sh does. And the browser session lives five minutes by design: when it expires the UI says so and returns you to sign-in rather than showing you empty tables.

What is not verified here, said plainly

  • The browser interactions. How this was built

This section is unusual in product documentation, and it is here deliberately. This project's distinguishing quality is not that it worked the first time — it is that its failures are recorded, explained, and turned into checks. If you are evaluating it, this is the part worth reading: everything below is a claim about how the project behaves when something goes wrong, and every one ends with the test that now catches it.

1 · A process hung for 31 hours and nothing restarted it

Jaeger — the trace viewer — stopped responding and stopped logging. The container stayed Running and its readiness probe went on reporting failure, forever. Nothing looked at the failure, because a readiness probe is a signal, not a restart: only a liveness probe tells Kubernetes to do something about it. The bring-up script, which waits for rollouts, could not finish — so the first-run path was broken for a day and a half and only a human could clear it.

Now: every container carries a liveness probe, with thresholds chosen per component — about a minute of silence for a stateless service, two minutes for Postgres, where a restart is the most expensive thing Kubernetes can do to it. The gateway also needed code, not a probe: its only listener is mTLS, and a kubelet has no SVID, so it serves /healthz and nothing else on a plaintext port.

And the verification taught its own lesson. The first attempt reported "not restarted" for four services, which looked like a finding about probes. It was a finding about the test: signals sent to a PID-namespace init process from inside the namespace are discarded — kubectl exec … kill -STOP 1 is a no-op, and the process stays in state S. It has to be signalled from the node, matched by cgroup. Fifteen containers were then hung and watched to recover.

2 · A TLS server served an expired certificate

The gateway fetches its identity at startup. Keycloak hands back its cached SVID, which may already be half spent, so a process that restarts on a fixed interval can find itself serving an expired certificate — every handshake fails, and the symptom names the wrong component: "the model could not be reached".

Now: the restart deadline is derived from the certificate's own notAfter (exit 120 seconds early), and gateway.svid_loaded reports expires_in_seconds at startup so the condition is visible before it bites.

3 · The identity registry lived in a file beside the server

SPIRE's registry was a SQLite file, so a restarted server forgot every agent and every entry — and the demo's script deleted Keycloak every run, so accounts did not survive either. Identity was durable in principle and ephemeral in practice.

Now: the registry, the realm and the application's own state live in Postgres, each with its own least-privilege role; SPIRE's signing keys are on a volume, so a restart keeps the same CA and no workload needs reissuing. This also inverted the demo's critical path — identity now needs the database — which is exactly why production points at a managed, replicated one.

4 · Two identity systems, and no hop that named its peer

The mesh encrypted everything, which felt like security and was not identity. No hop told the application who was calling, and POST /audit/events accepted no credential at all: any pod in the mesh could forge an audit record.

Now: every hop between workloads we own is SPIFFE on both sides, and the machine routes require the caller to be named. And the alternative was measured before it was rejected: taking our pods out of the mesh would have left all of their outbound hops unencrypted — a login through an uninjected API against a meshed Keycloak still returned 200, in plaintext. So the pods stay injected and only the SPIFFE port skips the proxy.

5 · The five-minute token expiry looked like data loss

The demo's sign-in tokens live 300 seconds, and the UI polls every five. When the token expired, the audit timeline's failed refresh set an empty array — so the page rendered "No events yet", which reads as the audit trail having been lost.

Finding the fix took measuring the API rather than assuming it. A missing token returns 401, but an expired one returns 403 — the same status a caller gets for lacking a role, so "sign out on 403" would have ejected people for lacking permission. The UI now expires the session from the token's own expires_at, with a narrow backstop that matches the API's token messages. And the audit page keeps its last good view and says it is stale.

Then it looked like the fix hadn't shipped. It had — the server sent no Cache-Control at all, so the browser applied heuristic caching and kept running a build several deploys old. The shell is now no-cache (revalidate, which the ETag makes cheap) and the hashed bundles are immutable.

6 · A user with a role, shown as having none

A demo user signed in with "no roles" — and then successfully issued a refund. Her token carried billing and policy honoured it; the API's list of platform roles was simply missing billing and read_only, so the display dropped them. Capability and display disagreed, and the display is what a person believes.

Now: the API serves the role list and the UI renders what it is given — one source instead of four — and two tests compare that source against the policy and against the realm seed, so either direction of drift fails the build. Restoring the old list makes both tests fail with the reason in the message; that was verified by doing it.

7 · Markup generated by a script that rendered the script

A facts row was added to a result card by generating JSX from a script, and the regex quantifier meant to match whitespace was written into the output as literal text. It compiled, it typechecked, and the class-coverage check passed — and it put [ ]* on the screen between every value. (An earlier version of the same mistake rendered {at(a.at)} as text, for the same reason.)

Now: markup is written by hand, regexes are used only to find code, and a test fails if any web source contains a whitespace regex fragment — the exact signature of the mistake. The deploy path also reads the built bundle for the same fragments.

8 · Claims that were not checks

Two example, both found while fixing something else. The roles suite printed "must be refused" and then whatever status came back — a 200 would have passed; it now asserts 403. And a probe of my own reported "not restarted" for every service, because the command it used to hang a process is silently discarded (see §1). An assertion is the difference between a claim and a check.

9 · A model swap found an assumption about where answers live

Swapping in a Qwen3 model for the demo's small one took the evals from 5/8 to 1/8 — every case failing with "the model's reply could not be understood". The model was answering correctly; it was answering somewhere else. With format: json, a thinking model returns response empty and puts the JSON in thinking:

the same call, straight from Ollama
response: ''
thinking: '{"tool": "refunds.quote", "args": {} }'   ← correct, and ignored

Now: the gateway asks for think: false and falls back to thinking for a model that ignores the request — the same model then scores 6/8. The same swap exposed a second assumption: llm.call recorded the model the caller named, and the agent names none, so the field that exists to answer "which model decided this?" had been recording an empty string. It now records the model resolved for the call, and a test asserts it.

What the project settled on

Every claim gets a check

If it is written down as behaviour, it has a test, a gate, or a suite.

A check must be able to fail

The new tests were validated by reverting the fix and watching them fail — with the reason in the message.

Do not test only what you just wrote

A deployment script's authenticated path was never exercised, and that is exactly where its bug lived.

Stubs must fail like the real thing

A stand-in that accepts anything proves only that the code runs. The test double now enforces required arguments, the way the real CLI does.

Regexes find, never generate

Two visible bugs came from generating markup with patterns instead of writing it.

When the page looks wrong, read the headers

A correct server and a stale browser are indistinguishable from the inside.

Limits and non-goals

Every system is honest only about the boundaries it states. These are the ones this platform names in its own documentation, rather than leaving to be discovered.

What it deliberately is not

Not an agent framework

It is the identity and authorization layer around an agent. The agent is LangGraph, the tool boundary is MCP, the policy engine is OPA — the project's contribution is the layer that makes those three accountable to a person's identity.

Not production infrastructure

One Postgres, on a node-local volume, is a demonstration choice. SPIRE can run two replicas with a shared KeyManager, but the database remains the shared dependency — which is why the chart takes a managed DSN.

Not a claim that one identity system sufficed

Two remain, and the boundary between them is the design (ADR-0012). The mesh is load-bearing for the software we did not write.

Not real data, ever

Everything is synthetic: customers, orders, refunds, personal data. The PCI-aware scoping is real in shape and fictional in content (ADR-0006, docs/data-handling.md).

The residuals, repeated on purpose

These are stated in the transport section and in the ADR, and they are repeated here because a limit you have to find is a limit you will miss:

ResidualConsequence
The ingress → api hop is plaintext in-clusterThe browser's hop is encrypted; the last leg inside the cluster is not, because the controller carries no sidecar. Meshing the controller closes it.
A machine caller's name rides a JWT-SVID, not the certificateOur ASGI server does not expose the peer certificate. The name is audience-bound, five minutes, never logged — but it is a bearer token, not a SAN assertion.
The mesh must be present for third-party encryptionWithout it, those hops are plaintext — and setup says so rather than pretending.
Cross-tenant isolation is enforced in the application and the policyNot by separate databases or clusters. For a shared deployment of this shape that is the right trade; for stricter isolation you would go further.
The threat model covers eleven threatsIt does not claim to cover categories outside it — availability under deliberate attack, or the security of the model provider's own systems, are out of scope and named as such.

Glossary

TermPlain meaning here
audience (aud)Which service a token is for. A token minted for the tool server is useless at the API.
attestationHow SPIRE satisfies itself that a node and pod are genuine before issuing an identity.
audit trailThe append-only record of what happened, keyed on identity, with secrets and personal data redacted before storage.
azpThe workload a token was issued to — the agent, typically. Checked as defence in depth.
bearer tokenA credential that works for whoever holds it. Short lifetimes and audience binding are how that risk is managed.
CA (certificate authority)The thing that signs certificates. Here, SPIRE's, rotated daily in the demo.
checkpointA saved agent state, in Postgres, so a paused run can resume.
cosign / SigstoreSigning artifacts without a stored key: the signature is tied to the CI workflow and logged publicly.
delegationActing on someone's behalf with a token that says so — never with their password.
deny by defaultNothing is permitted unless a rule permits it.
JWT · JWT-SVIDA signed JSON token; here, the form of an SVID used to say who is calling in a header.
JWKSThe published public keys a verifier uses to check a JWT's signature.
KeycloakThe identity provider: logins, tokens, and the token exchange.
kindKubernetes in Docker — the local cluster the demo runs on.
LangGraphThe library the agent is built with; its state machine is what makes pausing for approval natural.
LinkerdThe service mesh: mutual TLS for the hops we do not control the code of.
liveness vs readinessReadiness decides whether traffic is sent; liveness decides whether the process is restarted. Only liveness recovers a hang.
MCPModel Context Protocol — one of the two ways tools are exposed, funnelling through the same enforcement.
mTLSTLS where both sides present certificates, so each knows who the other is.
OPA · RegoThe policy engine and the language its rules are written in.
PEPPolicy enforcement point — the one place decisions are applied: the tool server.
RBACRoles bound to permissions; here, the role → tool matrix, per tenant.
RFC 8693The OAuth 2.0 Token Exchange standard: trading one token for another.
SPIFFE · SPIREThe standard for workload identity, and the implementation that issues it.
SVIDA workload's credential — an X.509 certificate or a signed JWT, both short-lived, both fetched rather than stored.
subThe subject a token is about: the user whose authority is being exercised.
tenantA customer of the platform. An identity attribute, not a parameter.
trust bundleThe set of CA certificates a verifier accepts. Its identity across replicas is what proves a shared key manager.
trust domainThe namespace identities are issued in — acme.com here, and documentation rather than a secret.
workloadAny program with an identity. In this platform, a pod's main container.
Workload APIThe in-pod socket a workload asks for its identity. No password is presented to it.
