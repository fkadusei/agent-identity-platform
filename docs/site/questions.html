Questions, answered

Every question I asked about this platform while learning it, with the answer the code and the running cluster give — not the answer a diagram suggests. New questions get added as they come up, and each answer says where to look, so you can check it rather than take it on faith.

How each answer is built If it is a fact about a file, the file is named. If it is a fact about behaviour, it was seen running — and where it was surprising, the answer says what surprised me. Three pages sit together: the overview explains the whole platform, the agent page follows one task through the code, and this page answers questions — including the ones the other two now had to change for.

01What is this platform, in a minute?

A control plane for AI agents. It answers one question, over and over, per action: "may this agent, acting for this person, in this tenant, do this — right now?" — and it answers it in code that does not trust the model.

The shape is four of our own services, one identity system underneath, and one place where a model is allowed to live:

PieceIts jobIt may
apiLogin, enrollment, approvals, audit, and the web appTalk to Keycloak; hold the admin client; proxy tasks to the agent
agentThe graph: plan → call a tool → ask → or pause for a personPropose actions. Hold no model credential
toolsThe enforcement point — the only place authority is grantedCall the downstream systems, after policy and any approval
gatewayThe only thing with the model provider's keyReach the model; count and cap spend per calling agent

Underneath: SPIRE gives every workload a name and a short-lived credential; Keycloak holds the people and issues their tokens; OPA decides per call; and Postgres keeps the things that must survive a restart — approvals, the audit trail, and paused runs. The phrase to keep in mind is the one the pages repeat: the model proposes, the platform disposes.

02Where are the users stored?

In Keycloak, in the realm agent-platform. The application keeps no user table of its own — it verifies a token and reads identity out of it.

03How do I show someone the users really exist?

Ask Keycloak, not the app. One command prints the users straight from Keycloak's Admin API; the console is two steps away if you want to click instead.

commands — one command, no setup, no admin password

./scripts/show-keycloak-users.sh

It runs inside the API pod, which is the whole trick: in there keycloak resolves by service name, so there is no port-forward, no /etc/hosts entry and no browser — and it reuses the API's own least-privilege client, so no master admin credential is involved. It reports 19 users today, including the leftover carol-*, norole and survivor that the test suites wrote.

For the console itself

commands — a hosts entry and a port-forward, then a browser

echo "127.0.0.1 keycloak" | sudo tee -a /etc/hosts      # once
kubectl --context kind-agent-platform -n agent-platform port-forward svc/keycloak 8080:8080

Then http://keycloak:8080/admin, sign in as admin/admin (demo-only, and only reachable this way — the ingress routes / to the API, so no admin console is exposed at the edge), switch the realm to agent-platform, and open Users. Per user, Role mapping is the role and Attributes is the tenant.

Two things that puzzle people otherwise Browsing localhost:8080 does not work: the realm pins the console's hostname, so the browser has to resolve the name keycloak — hence the hosts entry. And the realm holds more users than the demo, because the suites write to it: the realm is a live database, not a fixture.

05Is there one agent, or many?

One — and the platform is built for exactly one. One workload, one SPIFFE ID, held by two interchangeable replicas. Many runs happen at once, all as the same agent acting for different people.

The identity is spiffe://acme.com/ns/agent-platform/sa/agent, and the word workload is doing the work in that sentence: identity is issued per workload, not per replica, which is why both pods prove the same name. Registration is a rule about when an identity may be issued, binding a Kubernetes service account to a name:

scripts/setup.sh

ensure_entry() { # ensure_entry <service-account> <spiffe-id>
  local sa="$1" id="$2" entry parent
  # Drop any existing entries for this identity (e.g. parented to a node that is
  # gone), then register one per attested agent.
  for entry in $($SPIRE entry show -socketPath "$SOCKET" -spiffeID "$id" 2>/dev/null \
    | awk '/Entry ID/{print $NF}'); do
    $SPIRE entry delete -socketPath "$SOCKET" -entryID "$entry" >/dev/null
  done
  for parent in $($SPIRE agent list -socketPath "$SOCKET" 2>/dev/null \
    | awk '/SPIFFE ID/{print $NF}'); do
    $SPIRE entry create -socketPath "$SOCKET" \
      -spiffeID "$id" -parentID "$parent" \
      -selector "k8s:ns:$NS" -selector "k8s:sa:$sa" >/dev/null
  done
  ok "registration entry: $id (k8s:sa=$sa)"
}

Four workloads are registered that way: agent, gateway, api and tools. And policy then trusts one actor:

policy/authz.rego

trusted_agent := "spiffe://acme.com/ns/agent-platform/sa/agent"

A second agent would be refused as denied: untrusted workload identity until it is registered and the policy names it. That is not an accident of configuration — it is the current design, and question 10 is what changing it would take.

06What can the agent do now that it couldn't before?

Four things, and each one came from someone using it and finding it wanting. None of them changed what is permitted — they changed what the agent does with a thin task, and how honest the record is.

Ask instead of refusing S18

"Refund $200" with no order named used to end as a refusal. It now pauses and asks which order, because the person has the answer. Bounded at two asks; a tool the role may not call is still refused outright.

Take more than one step S19

"Refund the order from ticket t-5001" needs the ticket read first. The agent can now go round again with what the call returned — at most three steps, and only when it says it needs another. Every step is judged by policy on its own.

Pass identifiers along, never invent them S20

An identifier is kept only if the model has seen it — in the task or in an earlier tool result. Otherwise it is dropped, and the task's own value wins over the model's guess (see question 7).

"Allowed" stops meaning "it happened" S21

When the tool answers that it could not do the work, the screen says allowed — but nothing happened, and the tool's answer is recorded in the audit (see question 8).

The pattern in all four The model proposes; the platform disposes. S18–S20 make the agent better at conversing without giving it a gram more authority, and S21 makes the platform more honest about what happened. If one of these ever read as "the model got a new power", the design would have gone wrong — it is worth checking that when reading them.

07When something needs an approval, how does that work?

Yes — there is a real queue, and it is a Postgres table. A request that policy judges too risky is written down, the run pauses, and it stays paused until a different person decides. The queue is what the manager's Approvals tab reads, and its depth is what scales the API.

The path of one held action

  1. Policy says so. The tool server asks OPA, which answers require_approval for this caller, tool and arguments — e.g. a refund above $50 and no more than $500 — and returns 428 to the agent. Nothing has been executed.
  2. The agent writes the request down. It calls the API to create an approval, over a SPIFFE hop, and only the agent's workload identity is allowed to do that — creating an approval is the step that makes a high-risk action possible.
  3. The run pauses. The graph's await_decision node raises an interrupt, the run is checkpointed in Postgres, and the requester gets the approval id. The run can be resumed by any replica, and it survives a restart.
  4. A person decides. A manager (the Keycloak role) sees it in the queue and approves or denies, optionally with a note. The requester cannot decide their own request.
  5. The run resumes, and is judged again. The requester resumes it; the agent calls the tool with the approval id; the tool server verifies that the approval matches this exact request — six fields — and only then executes.

The queue itself

One row per request: the tool, its arguments as canonical JSON, the person it is for, the agent that asked, the reason, the tenant, the status, who decided it and when.

app/approvals/store.py — the table

CREATE TABLE IF NOT EXISTS approvals (
    id          text PRIMARY KEY,
    tool        text NOT NULL,
    args        jsonb NOT NULL,
    "user"      text NOT NULL,
    agent       text NOT NULL,
    reason      text NOT NULL,
    tenant      text NOT NULL DEFAULT '',
    status      text NOT NULL,
    approver    text,
    note        text,
    created_at  double precision NOT NULL,
    decided_at  double precision
);

There are two backends behind one interface: Postgres when a database is configured (durable, shared by all replicas, and what the demo runs), and in-memory for tests and single-process runs. The queue a person sees is their tenant's pending rows; the number the autoscaler sees counts every tenant, because queue depth is a property of the platform, not of one tenant or one replica.

Three things that make it more than a to-do list · Bound to the exact request. Verification compares the approval id, the tool, its arguments, the person, the agent and the tenant — so an approval for a $60 refund cannot be replayed for $600, or for someone else. · Separation of duties, in SQL. The decision is a single statement whose WHERE clause requires the row to still be pending, to be in the approver's tenant, and to not belong to them. Two managers clicking at once cannot both win, and nobody can approve their own request — enforced by the database, not by the UI. · An approval is not authorization. Policy runs again on the resumed call, and the tool server verifies rather than trusts.

app/approvals/store.py — the decision, and why it cannot race

08Why didn't it ask for the order?

Because the model supplied one — it answered with the field's own name as the value. The agent asks when a required argument is missing; a guess is not missing, so nothing asked, and a refund against an order literally called order_id went to a manager for approval.

Reproduced from a real run. The task was "Issue a refund of 200 dollars for order " — nothing after "order" — and the approval it created carried:

illustrative — the arguments the approval was bound to

{"amount": 200.0, "order_id": "order_id"}

Four steps, each behaving exactly as designed, which was the problem:

  1. The model replied {"tool": "refunds.issue", "args": {"order_id": "order_id", "amount": 200}}.
  2. The gap-filling code looked for an order in the task text, found none, and left the model's value alone.
  3. The guardrail that exists to catch missing arguments only checked that a required value was present and non-empty — and "order_id" is a non-empty string.
  4. Policy saw a well-formed $200 refund and held it for a manager.

The fix is a rule, not a patch: the model may pass along an identifier it has seen — in the task or in a tool result — and may never invent one. What counts as an identifier is the _id suffix, so amounts and free text are untouched:

app/agent/guardrails.py

def identifier_args(tool: Tool) -> list[str]:
    """The tool's required arguments that name something that exists in the world.

    The convention is the `_id` suffix — `customer_id`, `order_id`, `ticket_id`.
    These are facts the model cannot reason its way to; it either saw one or it is
    guessing, which is the distinction `resolve_identifiers` enforces.
    """
    required = (tool.input_schema or {}).get("required") or []
    return [name for name in required if name.endswith("_id")]
And the fix had a hole that only a retry found The first version searched the task text for the model's value — and retrying the same task then got through as {"order_id": "order"}, because the word "order" appears in "for order ". A word passed as an identifier. The comparison is now a set of identifier-shaped tokens, and both cases are tests, so the reported bug and its near-miss are pinned.

What you see now, five runs out of five: the same task comes back clarification_required · missing: order_id, and answering with the order proceeds into the manager approval it always needed. What the platform still does not do is check that an order exists before acting — that is the tool's job, and it is the next question.

09Why did a wrong order come back allowed?

Because "allowed" is policy's answer, not the tool's. Policy allowed the call — the amount was under the auto-approval limit — and the tool then discovered the order does not exist and said so. The screen showed policy's word and the tool's failure side by side, and "allowed" read as success.

The amount is what decides it:

TaskWhat policy saysWhat you saw
order z, $200the id is not an identifier at all → asksWhich order?
order o-9999, $200$200 > $50 → held for approvalHeld — a manager decides
order o-9999, $20≤ $50 → allowed, then the tool answersallowed + unknown order
The outcome was deliberate, and I did not reverse it Before changing anything I found a test that says so explicitly: test_a_missing_record_is_a_result_not_an_error — "asking for a record that is not there is an answer the caller can read, not a failure." A previous slice chose that on purpose. So the outcome stayed, and the two things genuinely wrong got fixed instead.
  1. The audit gap. The trail held only tool.allowed, which records the decision and not what came back — so "did the refund actually happen?" could not be answered from the audit at all. The tool's own answer is now recorded too: tool.reported_error, with the message.
  2. The display. "allowed" no longer stands alone: the chip reads allowed — but nothing happened, the step says the call was allowed and the tool answered unknown order, and the result block is headed The tool's answer.

commands — the trail, on the running cluster

tool.allowed          {"tool": "refunds.issue", "reason": "allowed: refunds.issue is within your role"}
tool.reported_error   {"tool": "refunds.issue", "reason": "unknown order"}

The honest limit that remains: an identifier that does not exist is something only the backend knows. The platform could check first — an extra read the person did not ask for, with its own policy question — and that is a design decision, not a bug fix.

10What is the cloud-provider work?

Letting the platform talk to a model outside the building — and deciding whether it should. The plumbing is in place; two defects in the hosted branch stop it working, and the interesting half is a policy question, not a code one.

Today the model runs locally (Ollama), which is a deliberate choice: when the agent reads personal data under an approval, nothing leaves the machine. What is already there:

  • the model is named in one place, and ./scripts/use-model.sh swaps it without rebuilding;
  • a slot for a provider key already exists, and only the gateway can read it — the agent holds no model credential at all;
  • only the gateway talks to a model; everything else asks it.

The two defects, both found by reading that path

SymptomCause
The request reaches the provider with no model named, and fails The gateway forwards the request it received; the agent deliberately sends no model (it should not care which vendor answers). The gateway works out the model for its own audit but does not put it into the forwarded request.
A strict provider may reject a "give me JSON" hint The agent already asks for JSON in words in the prompt, so dropping the formal hint is survivable — it just needs dropping when the provider does not accept it.
The question that makes it a slice rather than a patch Should a cloud model ever see customer data? Local-only means it cannot. Point the gateway at a provider and an approved PII read would send that data off-site. The platform's style would answer that with policy — a rule such as "this tool, or this tenant, may only use a local model" — and the two defects come along with it. This is S17, and it is the last open slice.

What "done" looks like: a fake OpenAI-compatible provider running in-cluster (so the path can be tested with nobody's cloud key), tests for those two defects, one live run against a real provider, and a written answer to the data question.

11What would many agents — and sub-agents — take?

There is no agent record anywhere. An agent exists by appearing in four registries owned by four different systems, and "registration" is a rule about when an identity may be issued — not a row about a robot.

WhatWhere it livesWhat is in it
Identity SPIRE's datastore (its own Postgres database, durable) A registration entry: service account + namespace → SPIFFE ID. Today created imperatively by the setup script
Delegation Keycloak's Postgres (the realm) A client whose clientId is the SPIFFE ID, authenticating with a JWT-SVID instead of a secret, with token exchange enabled and the audience/tenant mappers
Admission Each service's configuration Which SPIFFE IDs may call it, and whose token exchange its user tokens may carry. Both default to the one agent
Authorization The OPA bundle (policy in git, built and signed) Which agents are trusted, and the roles → tools matrix
The gateway needs no change It accepts any caller holding a JWT-SVID audienced to it, and keys its rate and cost limits on the proven caller. A second agent would simply get its own budget — the multi-agent story there is already done.

So a second agent is four edits

  1. SPIRE: give it a service account and a registration entry — the identity follows the workload.
  2. Keycloak: a client named by its SPIFFE ID, with the same three attributes and mappers. No secret: it signs with its JWT-SVID.
  3. Admission: add it to the allow-lists of the services it must reach. This is the knob that makes "which agents may talk to which services" a real decision — and the tool server additionally pins which agent's exchange its user tokens must come from.
  4. Policy: name it as trusted, and give it its own roles → tools matrix if it should differ. input.agent is already a policy input, so this is a natural extension.

Sub-agents are the interesting case: a chain, not just an identity

Today there is exactly one delegation hop — a person to the agent — using RFC 8693 token exchange. Agent A calling agent B needs three things, two of which are half-anticipated:

NeedState of play
The chain must name the path (person → A → B) RFC 8693 expresses this with the act (actor) claim, and the SDK already reads it in preference to the token's issuer. What is missing is producing it: the exchange accepts extra parameters, but nothing passes an actor token yet.
B must act as the same human, never as itself The subject stays the person's; A and B are added to the chain. A sub-agent acting purely as a service identity is a different thing and should not touch user data at all.
A sub-agent must get less, not more The exchange already takes a scope, so a parent can hand down a narrowed one. Policy should then decide per agent, because "may this agent refund for this user" is a different question from "may the agent".

The lifecycle of an agent

PhaseWhat happensToday
Register Service account + registration entry + Keycloak client + admission lists + policy grant, reviewed works but imperatively; production wants it declarative and reviewed, because it is a privilege decision
Attest (birth) The pod starts, SPIRE checks its Kubernetes service-account token, and hands it an X.509-SVID (1 h) and a JWT-SVID (5 min) over a Unix socket. No secret is provisioned, nothing lands on disk works — and this is why there is no password to leak or rotate by hand
Act (per request) Exchange the person's token for one scoped to the tool server → call tools over an mTLS hop naming itself → policy decides per call → the audit records the agent, the person and the tenant works
Delegate down Sub-agent calls, actor chaining, narrowed scope, per-agent policy new — identity and admission work; the chain and per-agent policy are the work
Rotate X.509 1 h, JWT 5 min, signing authority 24 h — fetched per use, no restart, no key to rotate works
Suspend / revoke Delete the registration entry (no new credentials), disable the client (no new exchanges), remove from the admission lists (calls refused), drop the policy grant new — and the honest caveat: a credential already issued stays valid until it expires, so revocation means stop issuing, not instantly dead
Decommission Remove all four, delete the workload the audit remains — who did what, on whose behalf, forever
Three decisions I would want made before any of it is built · Is an agent per-tenant or shared? Shared means one identity acting across tenants with the tenant taken from the person's token — today's model, and the safer default; per-tenant contains a compromise to one customer, at the cost of more identities and more policy. · Is the registry a privilege boundary? Adding an agent is adding a workload the platform will trust, so it deserves the scrutiny of a policy change: reviewed, and recorded. · Does a sub-agent inherit the parent's authority, or less? I would say strictly less, and make it enforceable rather than advisory.

12Disk or KMS for the identity keys?

Wherever SPIRE's KeyManager puts them — and that one setting decides whether the identity tier can be a failover pair. Every credential this platform issues is signed by a certificate authority, and that CA's private key has to live somewhere: on a volume, or inside a KMS. Two replicas can only serve the same trust bundle if they sign with the same CA.

First, a distinction that trips people up: the registry — the attested agents and registration entries — is already in Postgres, and always is. That half of HA was S1's first half. What switches here is only the key manager: where the signing key lives.

disk (default)aws_kms
Where the CA key is A file on the server's volume (/run/spire/data/keys.json), on a PVC so a restart keeps the same CA Inside AWS KMS. Created, rotated and used there — the private key never leaves
How many replicas One. The file cannot be shared, so two replicas would each mint their own CA — worse than a single server 2+ — every replica signs with the same key, so they serve the same bundle
What it needs Nothing. No credentials, no network. This is why an unattended demo uses it An AWS account, a KMS key's worth of permissions, and credentials that reach AWS
What a leaked credential means A file in your cluster reading a key in your cluster Still worth scoping: the recommended setup puts a role in front, so the long-lived credential can only assume it (below)
Critical path Volume + one pod Volume + pod + AWS KMS reachability and credentials

Both modes are blocks in one template, and the mode is a flag from the environment — so there is no second config file to drift:

illustrative — the two blocks, from the SPIRE server config template

KeyManager "aws_kms" {
  plugin_data {
    region                         = "<region>"
    key_identifier_value           = "<shared id>"
    enable_tag_based_key_discovery = true
  }
}
KeyManager "disk" {
  plugin_data {
    keys_path = "/run/spire/data/keys.json"
  }
}

Both directions are the same two steps: say so in .env, then run the setup script. Only the content of the first step differs.

Two things that decide whether the switch actually works · The shared identifier. The plugin's default identifier is a per-server file, which each replica would create for itself — one identifier each, one key each, a different CA each. SPIRE_KMS_SERVER_ID must be the same on every replica, and it cannot contain dots, which is why the trust domain's own name is written acme-com here. · Switching changes the CA. A KMS-backed server starts with a new CA (the disk one is a different key), and the demo rotates CAs every ~12 hours, so the gate compares the whole bundle rather than one certificate — otherwise it would keep matching across a change and pass the check that exists to catch it. Treat the switch as a maintenance window, not a flip.

Role-based access, which is the recommended shape

PrincipalHasWhy it is built that way
IAM user spire-kms-base only sts:AssumeRole on the role below This is the credential that sits in .env. If it leaks, it can try to assume one role and nothing else
IAM role spire-kms The KMS permissions that actually sign The plugin assumes it, and the AWS SDK refreshes the assumed-role credentials itself — so an expired session does not stop identity from starting, unlike static keys

The plugin creates and rotates its own keys — there is nothing to pre-create — so the role needs the permissions to list, describe, create, sign with and schedule deletion of KMS keys. That last one is why it should be a dedicated principal: a principal that can schedule key deletion can destroy an identity tier.

Measured, with KMS in us-east-1 Every SVID issuance is one Sign. From inside the cluster, fetching an identity took 5 ms (X.509-SVID, p50) and 18 ms (JWT-SVID, p50) — and the running cost is that request count against your region's KMS price. Checked against a live key: the plugin created its own P-256 signing keys, both replicas served a byte-identical trust bundle, and deleting a replica left the survivor issuing SVIDs with no workload restarted. The base credential behaved too — its own kms:ListAliases was denied, because it may only assume the role.

Why the demo still defaults to disk: running the CA in KMS makes identity depend on short-lived cloud credentials and a network path to a region — a dependency the demo would carry on every start for a benefit (two replicas instead of one) that a laptop cluster does not need. It is one line in .env away, and it is the mode a real deployment wants.
